Empat pilar desain Swift

Swift dirancang Apple bukan sekadar untuk produktivitas, tetapi untuk memindahkan kelas kesalahan dari runtime ke compile-time. Ini fondasi yang menjelaskan hampir semua keputusan sintaksisnya.

PilarImplikasi Praktis
Safety-firstOptional memaksa Anda menangani nil. Tidak ada null pointer exception yang tersembunyi.
Value semanticsstruct di-copy, bukan di-share. Menghilangkan seluruh kelas bug shared mutable state.
ExpressivenessEnum dengan associated value, pattern matching, dan generics membuat invalid state tidak bisa direpresentasikan.

Detail concurrency dibahas tuntas di Module 02; di sini cukup Anda tahu bahwa fondasi ini sudah berubah dari era Swift 5.

01Type System: let, var, dan Type Inference

Swift adalah statically & strongly typed dengan type inference yang kuat. Compiler menyimpulkan tipe dari nilai, tetapi tipe tetap dicek ketat saat compile.

Deklarasi dasar
// `let` = immutable binding (default & preferred). `var` = mutable.
let appName = "Alhazme"          // diinferensikan sebagai String
var retryCount = 0               // Int
let pi = 3.14159                 // Double
let isActive: Bool = true        // anotasi eksplisit

// Immutability adalah default yang Anda pilih secara sadar.
// `let` bukan sekadar konstanta — ia menjamin binding tidak berubah.
retryCount += 1                  // OK
// appName = "X"                 // compile error: cannot assign to value 'let'
Prinsip Enterprise Selalu mulai dengan let. Ubah ke var hanya ketika mutasi benar-benar dibutuhkan. Compiler bahkan memberi warning jika var tidak pernah dimutasi. Ini bukan gaya — immutability mengurangi permukaan bug konkurensi secara struktural.

Type safety vs implicit conversion

Swift tidak melakukan implicit numeric conversion. Ini disengaja untuk mencegah kehilangan presisi yang tak terlihat.

let count: Int = 10
let ratio: Double = 0.5
// let result = count * ratio   // ERROR: binary operator '*' cannot be applied
let result = Double(count) * ratio  // konversi eksplisit, hasil: 5.0

Type alias untuk domain clarity

typealias UserID = String
typealias Cents = Int

func charge(user: UserID, amount: Cents) { /* ... */ }
// Pembaca langsung paham domain-nya, bukan sekadar String & Int.

02Optionals — Jantung Keamanan Swift

Optional adalah fitur paling fundamental Swift. Ia mengkodekan "ketiadaan nilai" ke dalam type system. Sebuah String dijamin berisi string; sebuah String? mungkin berisi string atau nil. Compiler memaksa Anda menangani kasus nil sebelum mengakses nilainya.

Mental Model String? sebenarnya adalah Optional<String> — sebuah enum dengan dua case: .some(String) dan .none. Optional bukan magic; ia hanyalah enum biasa dengan dukungan sintaksis. Ini menjelaskan kenapa pattern matching bekerja sangat baik dengannya.

Lima cara aman membuka optional

1 & 2 — Optional binding (modern shorthand) + guard
let raw: String? = fetchToken()

// `if let` shorthand (Swift 5.7+): tak perlu lagi `if let token = token`
if let raw {
    print("Token: \(raw)")     // `raw` di sini bertipe String (non-optional)
}

// `guard let` — early exit, idiom utama di awal fungsi
func process(_ token: String?) {
    guard let token else { return }   // keluar jika nil
    // sisa fungsi: `token` dijamin non-nil
    send(token)
}
3, 4 & 5 — Nil-coalescing, optional chaining, force unwrap
// 3. Nil-coalescing: beri default
let name = userInput ?? "Guest"

// 4. Optional chaining: rangkai akses dengan aman
let city = order.customer?.address?.city   // String? — nil jika ada link putus

// 5. Force unwrap — TERLARANG di production kecuali invariant terbukti
let value = dictionary["key"]!   // crash jika nil — code smell
Anti-Pattern Force unwrap (!) dan implicitly unwrapped optional (String!) adalah penyebab crash nomor satu di aplikasi iOS. Di code review Alhazme, setiap ! harus dijustifikasi dengan komentar invariant, atau ditolak. Gantilah dengan guard let, ??, atau if let.
Optional sebagai dua jalur eksplisit — compiler memaksa Anda menangani keduanya.

03Value vs Reference — Konsep Paling Penting

Jika hanya satu konsep yang Anda kuasai dari modul ini, jadikan ini. Salah memahami value vs reference adalah sumber bug paling halus dan paling mahal di aplikasi iOS.

struct (Value type)class (Reference type)
Saat di-assign / dipassDi-copy (salinan independen)Di-share (referensi yang sama)
IdentityTidak ada — hanya nilaiAda — bisa dicek dengan ===
MutabilityDikontrol let/var di bindingInternal state bisa berubah meski let
MemoryStack (umumnya), no ARC overheadHeap, dikelola ARC
InheritanceTidak ada (pakai protocol)Ada
KonkurensiAman dibagi (Sendable mudah)Butuh proteksi (actor / lock)
Demonstrasi perbedaan inti
struct PointValue { var x: Int }
class  PointRef   { var x: Int; init(x: Int) { self.x = x } }

var a = PointValue(x: 1)
var b = a            // COPY
b.x = 99
print(a.x, b.x)      // 1 99  — a tidak terpengaruh

let p = PointRef(x: 1)
let q = p            // SHARE referensi yang sama
q.x = 99
print(p.x, q.x)      // 99 99 — keduanya menunjuk objek yang sama
Value type menyalin isi; reference type berbagi satu objek heap.

Aturan keputusan (default Apple)

  • Default ke struct. Gunakan untuk model data, DTO, state, value object — mayoritas tipe Anda.
  • Gunakan class hanya jika butuh: identity (objek yang sama harus dilacak), shared mutable state yang disengaja, interop dengan Objective-C/UIKit, atau lifecycle yang dikelola (mis. service singleton).
  • Untuk actor (reference type yang aman konkurensi) — dibahas di Module 02.
Jebakan untuk engineer Flutter/Dart Di Dart, hampir semua object adalah reference. Di Swift, kebalikannya — value type adalah default budaya. Jangan refleks membuat class. Membuat model sebagai struct menghilangkan seluruh kelas bug "object termutasi dari tempat tak terduga".

Mutating method pada struct

struct Counter {
    private(set) var value = 0
    mutating func increment() { value += 1 }   // wajib `mutating`
}
var c = Counter()
c.increment()        // OK karena `c` adalah var
// let d = Counter(); d.increment()  // ERROR: d immutable

04Enums & Pattern Matching — Sum Types yang Kuat

Enum Swift jauh melampaui konstanta bernama. Dengan associated values, enum menjadi sum type sejati — alat utama untuk membuat invalid state tidak bisa direpresentasikan.

Enum dengan associated value — memodelkan state
enum LoadState<Value> {
    case idle
    case loading
    case loaded(Value)
    case failed(Error)
}

// Tidak mungkin punya state "loaded tapi tanpa data" atau
// "loading sekaligus failed". State ilegal hilang by design.
func render(_ state: LoadState<[Order]>) {
    switch state {
    case .idle:               showPlaceholder()
    case .loading:            showSpinner()
    case .loaded(let orders): showList(orders)
    case .failed(let error):  showError(error)
    }
}
Prinsip Desain Pola LoadState di atas adalah idiom standar untuk view state di SwiftUI maupun UIKit. Ini menggantikan kombinasi flag boolean (isLoading, hasError, data) yang bisa menghasilkan kombinasi tak valid. Make illegal states unrepresentable — mantra arsitektur Swift.

Raw values & CaseIterable

enum HTTPStatus: Int {
    case ok = 200, notFound = 404, serverError = 500
}
let s = HTTPStatus(rawValue: 404)   // Optional<HTTPStatus> — .some(.notFound)

enum Plan: String, CaseIterable {
    case free, pro, enterprise
}
Plan.allCases.map(\.rawValue)       // ["free", "pro", "enterprise"]

Pattern matching lanjutan

switch httpStatus {
case .ok:
    proceed()
case .notFound, .serverError:           // multiple match
    retry()
}

// `where` clause & value binding di switch
switch order {
case let o where o.total > 1_000_000:   // `where` + numeric separator
    flagForReview(o)
default:
    process(order)
}

// `if case` untuk single-case match
if case .failed(let error) = state {
    log(error)
}

05Functions & Closures

Fungsi Swift punya argument label yang membentuk call-site yang membaca seperti kalimat — bagian penting dari API design ala Apple.

Argument label, default, variadic, inout
// `to` = external label, `recipient` = internal name
func send(_ message: String, to recipient: UserID, priority: Int = 0) { }
send("Hi", to: "u_123")               // call-site terbaca natural

// Variadic
func sum(_ numbers: Int...) -> Int { numbers.reduce(0, +) }

// inout — mutasi argumen asli (gunakan hemat)
func reset(_ value: inout Int) { value = 0 }
var x = 5; reset(&x)   // x == 0

Closures — first-class & trailing syntax

let numbers = [3, 1, 2]

// Closure penuh
let sorted = numbers.sorted(by: { (a: Int, b: Int) -> Bool in a < b })

// Type inference + trailing closure + shorthand args
let sorted2 = numbers.sorted { $0 < $1 }

// Multiple trailing closures (Swift 5.3+)
fetchData { result in
    handle(result)
} onProgress: { pct in
    updateBar(pct)
}
Capture & Retain Cycle Closure meng-capture variabel dari lingkungannya. Jika closure disimpan (escaping) dan menangkap self (sebuah class), Anda berisiko retain cycle. Solusinya: capture list [weak self]. Detail ARC & memory dibahas di Module 02 — namun ingat polanya sekarang: 
service.fetch { [weak self] result in
    guard let self else { return }
    self.update(result)
}

@escaping vs non-escaping

Closure default non-escaping (dijalankan sebelum fungsi return). Tandai @escaping jika closure disimpan untuk dipanggil belakangan (mis. completion handler async). Di kode modern, banyak completion handler digantikan async/await (Module 02).

06Error Handling

Swift memisahkan dengan tegas antara recoverable errors (pakai throws) dan programmer errors (pakai precondition/fatalError). Error adalah nilai biasa yang mengikuti protocol Error.

Mendefinisikan & melempar error
enum PaymentError: Error {
    case insufficientFunds(needed: Int)
    case cardDeclined
    case network(underlying: Error)
}

func charge(_ amount: Int, balance: Int) throws -> Receipt {
    guard balance >= amount else {
        throw PaymentError.insufficientFunds(needed: amount - balance)
    }
    return Receipt(amount: amount)
}
Menangani error — do/catch & varian try
do {
    let receipt = try charge(100, balance: 50)
    show(receipt)
} catch PaymentError.insufficientFunds(let needed) {
    promptTopUp(needed)
} catch {
    log(error)                       // `error` tersedia otomatis
}

// Varian try:
let r1 = try? charge(100, balance: 200)   // Receipt? — nil jika throw
let r2 = try! charge(100, balance: 999)   // crash jika throw — hindari

Typed throws — Swift 6

Old → New · Error Handling
Old (Swift 5) 
// Tipe error hilang —
// selalu `any Error`
func parse() throws -> Record {
   // caller tak tahu error apa
}
New (Swift 6+) 
// Tipe error eksplisit
func parse() throws(ParseError)
     -> Record {
   // caller dapat ParseError
}
Migrasi: Typed throws bersifat opt-in dan paling berguna di kode generik, library boundary, atau lingkungan resource-constrained (embedded). Untuk app code umum, throws (setara throws(any Error)) tetap idiomatik. Jangan over-engineer — gunakan typed throws hanya saat himpunan error benar-benar tertutup dan diketahui caller.

Result type

// Berguna saat error perlu disimpan/dioper sebagai nilai (mis. callback lama)
func load(completion: (Result<Data, NetworkError>) -> Void) { }

// Konversi ke throwing:
let data = try result.get()
Swift 6.4 — async defer Swift 6.4 (WWDC 2026) dilaporkan menambahkan dukungan defer async (mis. via proposal Swift Evolution terkait), sehingga cleanup resource asinkron terjamin di semua jalur exit — termasuk saat throw. Detail ini melewati basis pengetahuan terverifikasi saya; konfirmasikan nomor proposal & ketersediaan persisnya ke swift.org/Xcode release notes sebelum mengandalkannya: 
func fetch() async throws -> Data {
    let conn = try await open()
    defer { await conn.close() }     // dijamin jalan, baru di 6.4
    return try await conn.read()
}
Recoverable vs Programmer Error Jangan pakai throws untuk bug logika. Precondition yang gagal (mis. index out of bounds yang seharusnya mustahil) memakai precondition()/assert() — bukan error yang di-catch. Membungkus programmer error sebagai recoverable error menyembunyikan bug, bukan menanganinya.

07Collections & Control Flow

Tiga koleksi inti — semuanya value type — plus control flow yang berpusat pada keamanan (guard) dan ekspresivitas (switch).

Array, Set, Dictionary
var orders: [Order] = []              // Array — terurut, boleh duplikat
var tags: Set<String> = ["new"]       // Set — unik, tak terurut
var prices: [String: Int] = [:]       // Dictionary — key→value

prices["sku_1"] = 9_900
let p = prices["sku_2"] ?? 0          // akses dictionary → optional

// Functional transforms (lazy-aware, value-safe)
let totals = orders
    .filter { $0.isPaid }
    .map(\.total)
    .reduce(0, +)

guard sebagai gaya default

func handle(_ req: Request) {
    guard let user = req.user else { return }
    guard user.isActive else { return }
    guard let payload = req.body else { return }
    // happy path tetap rata, tidak ada nested pyramid of doom
    process(user, payload)
}
Idiom Enterprise Prefer guard untuk validasi di awal fungsi. Ia memaksa early-return dan menjaga happy-path tetap di indentasi terluar. if let dipakai saat Anda butuh nilai hanya di scope kecil; guard let saat nilai dibutuhkan di sisa fungsi.

for-in, where, dan ranges

for order in orders where order.isPaid {
    receipt(for: order)
}
for i in 0..<orders.count { }     // half-open range
for i in stride(from: 0, to: 100, by: 10) { }
Swift 6.4 — Iterable protocol Untuk kode performance-critical, Swift 6.4 menambah protocol Iterable yang meminjam elemen (bukan menyalin) saat iterasi — relevan untuk noncopyable types seperti Span/InlineArray. Untuk app code biasa, for-in via Sequence tetap default. Disinggung di sini sebagai sinyal arah ekosistem; mendalam di Module 08 (Performance).

08Latihan

Kerjakan tanpa melihat solusi terlebih dahulu. Setiap latihan menargetkan kesalahpahaman umum di level senior.

EX 01

Refactor force-unwrap

Diberi kode rapuh berikut, refactor agar bebas crash menggunakan idiom optional yang tepat.

func greeting(for id: String, in users: [String: String]) -> String {
    let name = users[id]!
    return "Halo, " + name
}
▸ Lihat solusi 
func greeting(for id: String, in users: [String: String]) -> String {
    guard let name = users[id] else { return "Halo, Guest" }
    return "Halo, \(name)"
}
// Atau ringkas: "Halo, \(users[id] ?? "Guest")"

Kunci: ! pada dictionary lookup selalu salah — hasilnya inherently optional.

EX 02

Value vs reference

Apa output kode ini, dan kenapa? Lalu ubah Cart menjadi struct — apa yang terjadi?

class Cart { var items: [String] = [] }
let a = Cart(); a.items.append("apel")
let b = a; b.items.append("jeruk")
print(a.items)
▸ Lihat solusi

Output: ["apel", "jeruk"]. a dan b menunjuk objek class yang sama (reference), jadi mutasi via b terlihat di a.

Jika Cart diubah jadi struct, let b = a menyalin nilai. Tetapi karena b dideklarasikan let, b.items.append tidak akan compile — Anda perlu var b = a. Setelah itu, a.items tetap ["apel"] karena salinan independen.

EX 03

Modelkan state dengan enum

Sebuah upload bisa: belum mulai, sedang berjalan (dengan progress 0–100), sukses (dengan URL), atau gagal (dengan error). Modelkan agar invalid state mustahil, lalu tulis switch yang menanganinya.

▸ Lihat solusi 
enum UploadState {
    case pending
    case uploading(progress: Double)
    case success(url: URL)
    case failure(Error)
}

func describe(_ s: UploadState) -> String {
    switch s {
    case .pending:                  return "Menunggu"
    case .uploading(let p):         return "Mengunggah \(Int(p))%"
    case .success(let url):         return "Selesai: \(url)"
    case .failure(let e):           return "Gagal: \(e)"
    }
}

Kunci: progress hanya ada di .uploading, URL hanya di .success. Tidak mungkin "sukses tanpa URL".

EX 04

Error handling berlapis

Tulis fungsi withdraw(amount:from:) yang melempar PaymentError.insufficientFunds(needed:) bila saldo kurang, lalu tangani di call-site dengan menampilkan jumlah top-up yang dibutuhkan.

▸ Lihat solusi 
enum PaymentError: Error { case insufficientFunds(needed: Int) }

func withdraw(amount: Int, from balance: Int) throws -> Int {
    guard balance >= amount else {
        throw PaymentError.insufficientFunds(needed: amount - balance)
    }
    return balance - amount
}

do {
    let remaining = try withdraw(amount: 150, from: 100)
    print("Sisa saldo: \(remaining)")
} catch PaymentError.insufficientFunds(let needed) {
    print("Top-up dibutuhkan: \(needed)")
}

09Quiz, Mini-Project, Challenge & Referensi

Quiz Cepat

Jawab dulu di kepala, lalu buka jawaban. Bila ada yang meleset, ulangi bagian terkait.

Q1

Value vs reference

Anda menyalin sebuah struct ke variabel lain lalu mengubah salinannya. Apakah aslinya ikut berubah? Bagaimana bila class?

▸ Jawaban

struct = value type: salinan independen, asli tak berubah. class = reference type: keduanya menunjuk instance sama, perubahan terlihat di keduanya. Default pilih struct; pakai class saat butuh identitas/berbagi state.

Q2

Optional

Apa beda if let, guard let, dan ?? dalam menangani optional?

▸ Jawaban

if let: bind di dalam scope kecil. guard let: bind & keluar lebih awal bila nil (early return, mengurangi nesting). ??: beri nilai default. Utamakan guard untuk validasi di awal fungsi.

Q3

Error handling

Kapan memakai throws vs mengembalikan Result vs optional?

▸ Jawaban

throws: alur sinkron dengan propagasi error natural (do/catch). Result: saat error perlu disimpan/dilewatkan sebagai nilai (mis. callback lama). Optional: saat ketiadaan nilai bukan "error" bermakna. Di kode async modern, async throws adalah default.

Mini-Project

Bangun: model domain e-commerce miniBuat model tipe untuk keranjang belanja: Product (struct: id, name, price sebagai Decimal), CartItem (product + quantity), dan Cart (kumpulan item) dengan computed property total. Tambahkan enum CartError (mis. emptyCart, invalidQuantity) dan fungsi checkout() throws yang memvalidasi. Gunakan value types, optional yang tepat, dan error handling. Tujuan: melatih pemilihan struct vs class, Decimal untuk uang, dan throws untuk validasi.

Challenge

Naik levelPerluas Cart agar mendukung diskon polimorfik: definisikan protocol Discount { func apply(to subtotal: Decimal) -> Decimal } dengan beberapa implementasi (persentase, potongan tetap, beli-N-gratis-1). Cart.total menerapkan daftar diskon berurutan. Tantangan: rancang agar penambahan jenis diskon baru tak mengubah kode Cart (Open/Closed Principle) — fondasi menuju protocol-oriented (M02).

Common Mistakes

  • Memakai class sebagai default — kebiasaan dari bahasa lain; di Swift utamakan struct, gunakan class hanya saat butuh identitas/warisan/berbagi state.
  • Force-unwrap ! sembarangan — crash saat nil. Gunakan guard let/if let/??; simpan ! hanya untuk invarian yang benar-benar dijamin.
  • Double untuk uang — galat presisi. Pakai Decimal (relevan fintech/e-commerce).
  • Menelan error dengan try? di mana-mana — menyembunyikan kegagalan. Tangani atau propagasikan secara sadar.
  • Optional bersarang dalam — pertimbangkan model tipe yang lebih baik (enum, tipe non-opsional) alih-alih ?? berlapis.
