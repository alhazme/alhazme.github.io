MODULE 08 · PHASE 4 — ENTERPRISE ARCHITECTUREArsitektur: Mengelola Kompleksitas

Arsitektur bukan tentang "pola yang benar", melainkan tentang menempatkan keputusan agar perubahan murah. Module ini menelusuri evolusi pola iOS dan, yang lebih penting, kapan masing-masing tepat.

MVVMCleanTCA~110 menit

Tiga properti yang dikejar semua pola arsitektur:

  • Testability — logika bisnis dapat diuji tanpa UI/jaringan.
  • Separation of concerns — tiap unit punya satu alasan untuk berubah (SRP).
  • Independensi framework — bisnis logic tidak terikat SwiftUI/URLSession/SwiftData.
Sikap PrincipalOver-engineering sama berbahayanya dengan under-engineering. Aplikasi kecil dengan VIPER penuh membuang waktu; aplikasi enterprise dengan view controller gemuk runtuh saat skala. Tugas Anda: mencocokkan berat arsitektur dengan kompleksitas & umur produk.

01MVC & Masalah "Massive View Controller"

MVC bawaan Apple: Model–View–Controller. Secara teori bersih; dalam praktik, controller menjadi tempat pembuangan segala hal — networking, parsing, navigasi, validasi, format — menghasilkan Massive View Controller ribuan baris yang mustahil diuji.

GejalaViewController > 500 baris, memanggil URLSession langsung, menyimpan business state, dan mengandung logika navigasi. Tidak ada satupun yang bisa diunit-test tanpa memuat UIKit. Semua pola berikut pada dasarnya adalah cara berbeda untuk memindahkan logika keluar dari View/Controller.

02MVVM

Memindahkan presentation logic & state ke ViewModel yang tidak tahu apa-apa tentang View. Dengan Observation framework (Module 6), ViewModel adalah @Observable class.

enum ViewState<T> { case idle, loading, loaded(T), failed(String) }

@Observable
final class OrderListViewModel {
    private(set) var state: ViewState<[Order]> = .idle
    private let fetchOrders: FetchOrdersUseCase   // dependency via protocol/abstraksi

    init(fetchOrders: FetchOrdersUseCase) { self.fetchOrders = fetchOrders }

    func load() async {
        state = .loading
        do { state = .loaded(try await fetchOrders.execute()) }
        catch { state = .failed(error.localizedDescription) }
    }
}
Kunci MVVM yang benarViewModel tidak meng-import SwiftUI/UIKit dan dependency-nya disuntik (bukan dibuat di dalam). Itu yang membuatnya bisa diuji murni. MVVM yang memanggil URLSession langsung di dalam ViewModel hanyalah Massive ViewModel — masalah yang sama, lokasi berbeda.

03Clean Architecture

Clean Architecture menyusun kode dalam lapisan konsentris dengan satu Dependency Rule: dependency hanya boleh mengarah ke dalam. Lapisan dalam (domain) tidak tahu apa-apa tentang lapisan luar (UI, data).

Domain murni Swift — tanpa import framework. Data & Presentation bergantung ke Domain, bukan sebaliknya.
Domain — entity, use case, repository protocol
// Domain layer — TIDAK import SwiftUI/URLSession/SwiftData
struct Order: Equatable { let id: String; let total: Decimal }

protocol OrderRepository {                          // abstraksi milik domain
    func fetchAll() async throws -> [Order]
}

struct FetchOrdersUseCase {                         // satu aksi bisnis
    let repository: OrderRepository
    func execute() async throws -> [Order] {
        try await repository.fetchAll()
    }
}
Data — implementasi repository + DTO mapping
struct OrderDTO: Decodable { let id: String; let total_amount: Double
    func toDomain() -> Order { Order(id: id, total: Decimal(total_amount)) }
}

final class OrderRepositoryImpl: OrderRepository {  // implementasi milik data
    let network: NetworkService
    init(network: NetworkService) { self.network = network }
    func fetchAll() async throws -> [Order] {
        let dtos: [OrderDTO] = try await network.get("/orders")
        return dtos.map { $0.toDomain() }           // DTO → domain entity
    }
}
Kenapa repository protocol di domainInilah Dependency Inversion: domain mendefinisikan kontrak (OrderRepository), data menyediakan implementasi. Domain tak pernah tahu data datang dari URLSession atau cache. Saat testing, Anda suntik mock repository — use case teruji tanpa jaringan. Ini persis pola yang Anda jalankan di Flutter clean architecture.

04VIPER

VIPER memecah tiap layar menjadi lima peran: View, Interactor (business logic), Presenter (format untuk view), Entity, Router (navigasi). Sangat eksplisit, sangat granular.

KomponenTanggung jawab
ViewRender & teruskan aksi user ke Presenter
InteractorBusiness logic, panggil use case/repository
PresenterAmbil data dari Interactor, format untuk View
EntityModel data
RouterNavigasi antar-modul (mirip Coordinator)
Kapan & kapan tidakVIPER memberi boundary sangat tegas dan cocok untuk tim besar pada modul yang stabil & kompleks. Biayanya: banyak file & protokol per layar (boilerplate tinggi). Untuk app SwiftUI modern, mayoritas tim memilih MVVM + Clean ketimbang VIPER penuh karena Observation framework + use case sudah memberi pemisahan yang cukup dengan boilerplate jauh lebih sedikit.

05TCA — The Composable Architecture

TCA (Point-Free) adalah arsitektur unidirectional berbasis State, Action, dan Reducer — terinspirasi Redux/Elm. Negara aplikasi tunggal & dapat dikomposisi; semua perubahan melalui action.

import ComposableArchitecture

@Reducer
struct OrdersFeature {
    @ObservableState
    struct State: Equatable { var orders: [Order] = []; var isLoading = false }

    enum Action { case onAppear, ordersLoaded([Order]) }

    @Dependency(\.orderClient) var orderClient

    var body: some ReducerOf<Self> {
        Reduce { state, action in
            switch action {
            case .onAppear:
                state.isLoading = true
                return .run { send in await send(.ordersLoaded(try await orderClient.fetch())) }
            case let .ordersLoaded(orders):
                state.orders = orders; state.isLoading = false
                return .none
            }
        }
    }
}
Trade-off TCAKekuatan: aliran data sangat dapat diprediksi & diuji (reducer = fungsi murni), composability tinggi, navigasi state-driven, dependency injection terpusat. Biaya: kurva belajar curam (banyak konsep: reducer, effect, dependency, store), boilerplate untuk layar sederhana, dan kebergantungan pada ekosistem & versi library pihak ketiga. Tepat untuk app besar-modular dengan tim yang berinvestasi; berlebihan untuk app kecil. API TCA berevolusi — verifikasi terhadap rilis terbaru saat mengadopsi.

07Latihan

EX 01

Diagnosa Massive ViewModel

Sebuah ViewModel memanggil URLSession.shared.data langsung, mem-parse JSON, dan menyimpan token. Sebutkan tiga pelanggaran dan perbaikannya.

▸ Lihat solusi & review

(1) Networking di ViewModel → pindah ke Repository/NetworkService di belakang protocol. (2) Parsing di ViewModel → ke DTO + mapping di data layer. (3) Menyimpan token → ke secure storage (Keychain) via abstraksi.

Review: ViewModel seharusnya hanya: menerima dependency, memanggil use case, memetakan hasil ke ViewState. Sisanya milik lapisan lain.

EX 02

Susun Clean layers

Untuk fitur "profil user", tentukan apa yang masuk Domain, Data, dan Presentation.

▸ Lihat solusi & review

Domain: User entity, UserRepository protocol, GetProfileUseCase. Data: UserDTO, UserRepositoryImpl, remote/local data source. Presentation: ProfileView, ProfileViewModel.

Review: Repository protocol ada di Domain; implementasinya di Data. Dependency selalu menunjuk ke Domain.

EX 03

Use case

Tulis PlaceOrderUseCase yang memvalidasi cart tidak kosong lalu memanggil repository.

▸ Lihat solusi & review 
enum OrderError: Error { case emptyCart }
struct PlaceOrderUseCase {
    let repository: OrderRepository
    func execute(cart: [Item]) async throws -> Order {
        guard !cart.isEmpty else { throw OrderError.emptyCart }
        return try await repository.place(cart)
    }
}

Review: Aturan bisnis ("cart tak boleh kosong") hidup di use case domain — bukan di View atau Repository. Ini membuatnya teruji & dipakai ulang lintas UI.

EX 04

Pilih arsitektur

Pilih pola untuk: (a) MVP marketplace 6 layar, tim 1 orang; (b) super-app perbankan, 40+ modul, tim 30 engineer.

▸ Lihat solusi & review

(a) MVVM (+ Clean ringan) — cepat, cukup testable, boilerplate minimal untuk solo. (b) Modular + Clean, pertimbangkan TCA/VIPER per modul — boundary tegas penting saat banyak engineer & modul.

Review: Kesalahan umum: memaksakan TCA/VIPER pada (a) → memperlambat solo founder; memakai MVVM polos pada (b) → boundary kabur saat skala tim.
