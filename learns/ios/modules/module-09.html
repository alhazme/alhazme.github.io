MODULE 09 · PHASE 4 — ENTERPRISE ARCHITECTUREModularization & Dependency Injection

Clean Architecture (Module 8) memisahkan lapisan. Modularization memisahkan fitur ke unit fisik (SPM package), dan DI menyatukannya tanpa kopling keras. Bersama, keduanya membuat codebase besar tetap dapat dikelola solo atau tim.

SPMDI~95 menitMulti-tenant ready

Empat manfaat konkret modularization:

  • Build time — perubahan satu modul tidak meng-recompile seluruh app.
  • Boundary tegas — modul hanya bisa memakai API publik modul lain.
  • Ownership — tiap modul punya pemilik & test sendiri.
  • Reuse — modul Core (networking, design system) dipakai lintas proyek/klien — selaras model "build once, scale many" Anda.

01SPM Local Packages

Modularisasi modern memakai local Swift Package (bukan framework target lawas). Tiap modul adalah package dengan API publik eksplisit.

MyApp.xcodeproj
Packages/
├─ CoreNetworking/        // Package.swift — NetworkService
├─ CorePersistence/       // Keychain, SwiftData store
├─ DesignSystem/          // token + komponen (Module 6)
├─ DomainOrders/          // entity + use case + repository protocol
└─ FeatureOrders/         // View + ViewModel (depends: Domain, DesignSystem)
Package.swift — kontrol akses & dependency
// swift-tools-version: 6.0
let package = Package(
    name: "FeatureOrders",
    platforms: [.iOS(.v27)],
    products: [.library(name: "FeatureOrders", targets: ["FeatureOrders"])],
    dependencies: [
        .package(path: "../DomainOrders"),
        .package(path: "../DesignSystem")
    ],
    targets: [
        .target(name: "FeatureOrders", dependencies: ["DomainOrders", "DesignSystem"],
            swiftSettings: [.defaultIsolation(MainActor.self)]),   // UI module → MainActor
        .testTarget(name: "FeatureOrdersTests", dependencies: ["FeatureOrders"])
    ]
)
Kontrol akses sebagai boundaryHanya tipe public yang terlihat lintas modul. Ini memaksa Anda mendesain API modul secara sadar — internal detail tetap tersembunyi. Ingat (Module 3): set .defaultIsolation(MainActor.self) untuk modul UI; biarkan default nonisolated untuk modul logic/networking.

02Dependency Direction

Aturan emas: dependency mengalir dari fitur → domain → core, tidak pernah sebaliknya, dan fitur tidak saling bergantung langsung.

Fitur tak saling impor. Komunikasi lintas-fitur lewat Domain atau event, bukan dependency langsung.
Anti-PatternFeatureOrders meng-import FeatureAuth secara langsung menciptakan circular dependency dan merusak independensi build. Bila Orders butuh status auth, ekspos lewat abstraksi di Domain/Core (mis. AuthStateProviding protocol) yang keduanya bergantung padanya.

03Dependency Injection

DI = objek menerima dependency-nya dari luar, bukan membuatnya sendiri. Bentuk paling tahan lama: constructor injection.

Kopling keras → DI
Hard-coupled 
final class OrderVM {
  // membuat sendiri →
  // tak bisa di-mock
  private let repo =
    OrderRepositoryImpl(
      network: .init())
}
Constructor injection 
final class OrderVM {
  private let repo: OrderRepository
  init(repo: OrderRepository) {
    self.repo = repo   // disuntik
  }
}
// test: OrderVM(repo: MockRepo())
Alasan: dengan dependency disuntik sebagai protocol, Anda dapat menukar implementasi nyata dengan mock saat testing, atau implementasi berbeda per environment/tenant — tanpa mengubah konsumen. Constructor injection membuat dependency eksplisit & wajib (tak ada dependency tersembunyi).
Hierarki preferensi DI(1) Constructor injection — default, paling eksplisit & teruji. (2) Environment (SwiftUI) — untuk dependency UI yang dibagikan luas. (3) Property/container — hanya bila konstruktor tak praktis. Hindari singleton global (.shared) sebagai mekanisme DI utama — ia menyembunyikan dependency & menyulitkan test.

04DI Container & Composition Root

Di satu tempat (composition root, dekat entry point) Anda merakit graph dependency. Bisa manual (factory) atau dengan library (Swinject — Module 11).

Composition root manual — factory sederhana
@MainActor
final class AppContainer {
    // shared singletons (dependency level rendah)
    private lazy var network: NetworkService = DefaultNetworkService(baseURL: Config.apiURL)
    private lazy var orderRepository: OrderRepository = OrderRepositoryImpl(network: network)

    // factory untuk objek per-layar
    func makeOrderListViewModel() -> OrderListViewModel {
        OrderListViewModel(fetchOrders: FetchOrdersUseCase(repository: orderRepository))
    }
}

// Di entry point
@main struct MyApp: App {
    @State private var container = AppContainer()
    var body: some Scene {
        WindowGroup { OrderListView(viewModel: container.makeOrderListViewModel()) }
    }
}
Prinsip Composition RootSemua "new" yang merakit graph terjadi di satu tempat dekat root. Sisanya hanya menerima dependency. Ini menjaga modul fitur bebas dari pengetahuan cara membangun dependency-nya — fondasi reusability lintas klien (build once, scale many).

05Repository Pattern

Repository menyembunyikan sumber data di balik kontrak domain. ViewModel/use case tidak tahu data datang dari jaringan, cache, atau keduanya.

// Domain — kontrak
protocol OrderRepository {
    func fetchAll() async throws -> [Order]
}

// Data — implementasi dengan strategi cache-then-network
final class OrderRepositoryImpl: OrderRepository {
    let remote: OrderRemoteDataSource
    let local: OrderLocalDataSource
    init(remote: OrderRemoteDataSource, local: OrderLocalDataSource) {
        self.remote = remote; self.local = local
    }
    func fetchAll() async throws -> [Order] {
        do {
            let fresh = try await remote.getOrders().map { $0.toDomain() }
            try await local.save(fresh)               // refresh cache
            return fresh
        } catch {
            return try await local.loadAll()           // fallback offline
        }
    }
}
KekuatanLogika offline/cache terpusat di satu tempat (repository), bukan tersebar di banyak ViewModel. Mengganti backend, menambah cache, atau pindah dari REST ke GraphQL hanya menyentuh data layer — domain & presentation tak berubah. Inilah inti offline resilience untuk app SaaS Anda.

06Latihan

EX 01

Dependency direction

FeatureCheckout perlu tahu apakah user login. Ia tergoda meng-import FeatureAuth. Apa solusi yang benar?

▸ Lihat solusi & review

Definisikan protocol AuthStateProviding di Domain/Core; FeatureAuth menyediakan implementasi, FeatureCheckout bergantung pada protocol di Core — bukan pada FeatureAuth. Suntik implementasinya di composition root.

Review: Ini mencegah circular dependency & menjaga fitur independen. Komunikasi lintas-fitur selalu lewat abstraksi bersama, tak pernah impor langsung.

EX 02

Constructor injection

Refactor agar ProfileViewModel dapat di-mock saat test.

final class ProfileViewModel {
    private let repo = UserRepositoryImpl(network: DefaultNetworkService())
}
▸ Lihat solusi & review 
final class ProfileViewModel {
    private let repo: UserRepository
    init(repo: UserRepository) { self.repo = repo }
}
// test: ProfileViewModel(repo: MockUserRepository())

Review: Dependency menjadi protocol yang disuntik. Test kini bisa memberi mock deterministik tanpa jaringan nyata.

EX 03

Cache-then-network repository

Rancang repository yang mengembalikan cache dulu (cepat) lalu memperbarui dari network. Apa pertimbangan API-nya?

▸ Lihat solusi & review

Opsi: kembalikan AsyncStream<[Order]> yang meng-emit dua kali (cache lalu fresh), atau dua method (cached() + refresh()). Pilih sesuai kebutuhan UI.

Review: Kunci: keputusan strategi cache hidup di repository, bukan ViewModel. ViewModel hanya mengonsumsi hasil. Ini menjaga presentation tetap tipis.

EX 04

Pecah ke modul

App Anda punya fitur Auth, Orders, dan Profile plus networking & design system bersama. Usulkan struktur package + dependency-nya.

▸ Lihat solusi & review

CoreNetworking, DesignSystem (tanpa dependency fitur). Domain (entity + use case + repository protocol). FeatureAuth/Orders/Profile → depend ke Domain + DesignSystem (+ Core lewat Domain). App target merakit semua di composition root.

Review: Tidak ada fitur yang depend ke fitur lain. Core & DesignSystem reusable lintas klien — modal utama model bisnis "build once, scale many".
