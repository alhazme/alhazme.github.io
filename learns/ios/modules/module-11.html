01Dependency Injection — Swinject

Module 9 memakai composition root manual. Swinject menambah container dengan registrasi & resolusi terpusat — berguna saat graph dependency menjadi besar.

import Swinject

let container = Container()
container.register(NetworkService.self) { _ in AlamofireNetworkService() }
    .inObjectScope(.container)                      // singleton dalam container
container.register(OrderRepository.self) { r in
    OrderRepositoryImpl(network: r.resolve(NetworkService.self)!)
}
container.register(OrderListViewModel.self) { r in
    OrderListViewModel(fetchOrders: FetchOrdersUseCase(repository: r.resolve(OrderRepository.self)!))
}

let vm = container.resolve(OrderListViewModel.self)!
Trade-offManfaat: registrasi terpusat, scope (singleton/transient) mudah. Biaya: resolusi runtime (force-unwrap resolve bisa crash bila lupa register — kesalahan yang ditemukan saat runtime, bukan compile-time). Untuk solo founder dengan graph sedang, composition root manual (Module 9) sering lebih aman karena dicek compiler. Pakai Swinject saat graph benar-benar besar & banyak scope.

02Reactive — Combine & RxSwift

Status 2026 · Reactive di iOS
Dulu dominan

RxSwift — reactive lintas-platform, kaya operator. Combine — framework reactive Apple (iOS 13+).

Tren 2026

async/await + Observation menjadi default untuk mayoritas kebutuhan. Combine dipakai untuk kasus stream spesifik; RxSwift sebagian besar terbatas di codebase lama.

Arahan: Untuk kode baru, gunakan async/await (Module 3) + Observation (Module 6) lebih dulu. Combine masih relevan untuk: debounce/throttle search input, menggabungkan beberapa publisher, dan binding Combine-native dari SDK. RxSwift jarang dipilih untuk proyek baru. Apple memperlambat pengembangan Combine; verifikasi kebutuhan reactive Anda benar-benar tidak terpenuhi async/await sebelum menambah dependency reactive.
Combine untuk debounce search — kasus yang masih pas
import Combine
final class SearchModel {
    @Published var query = ""
    private var bag = Set<AnyCancellable>()
    init() {
        $query
            .debounce(for: .milliseconds(300), scheduler: RunLoop.main)
            .removeDuplicates()
            .sink { [weak self] term in Task { await self?.search(term) } }
            .store(in: &bag)
    }
    func search(_ term: String) async { /* ... */ }
}

03Database — Core Data & Realm

Module 5 membahas SwiftData & Core Data native. Di sini posisi pihak ketiga:

Penting — status Realm 2026MongoDB mengumumkan deprecation Atlas Device SDKs (Realm) dan Atlas Device Sync, dengan end-of-life sync pada 30 September 2025. Database lokal Realm tetap ada sebagai proyek open-source (Apache 2.0), tetapi tanpa dukungan resmi MongoDB dan fitur sync sudah mati. Untuk proyek baru, jangan pilih Realm kecuali ada alasan kuat & Anda siap memelihara fork-nya. Default ke SwiftData (Module 5) atau Core Data. Verifikasi status terkini sebelum mengandalkan Realm — situasi proyek open-source bisa berubah.

04Image Loading — Kingfisher

Memuat gambar remote dengan cache, downsampling, dan placeholder. Salah satu library yang manfaatnya masih jelas — menulisnya sendiri (cache disk+memory, cancellation, downsampling) memakan banyak kerja.

import Kingfisher

// SwiftUI
KFImage(URL(string: order.thumbnailURL))
    .placeholder { ProgressView() }
    .downsampling(size: CGSize(width: 120, height: 120))   // hemat memori
    .cacheOriginalImage()
    .fade(duration: 0.2)
CatatanApple punya AsyncImage native, tetapi Kingfisher unggul dalam kontrol cache, downsampling, dan prefetch untuk list panjang. Untuk app dengan banyak gambar (e-commerce, social), Kingfisher dibenarkan. Untuk beberapa gambar sederhana, AsyncImage native cukup.

05Animation — Lottie

Menjalankan animasi vektor (JSON dari After Effects) untuk onboarding, empty state, loading. Memberi animasi kompleks tanpa menggambarnya di kode.

import Lottie

struct LoadingAnimation: UIViewRepresentable {     // bungkus untuk SwiftUI
    func makeUIView(context: Context) -> LottieAnimationView {
        let view = LottieAnimationView(name: "loading")
        view.loopMode = .loop
        view.play()
        return view
    }
    func updateUIView(_ uiView: LottieAnimationView, context: Context) {}
}
Catatan UXLottie kuat untuk delight (onboarding, success state), tetapi animasi besar/banyak dapat membebani CPU & baterai. Gunakan terukur; untuk transisi UI biasa, animasi native SwiftUI (Module 6) lebih ringan.

06Analytics & Crash Reporting

Wajib untuk app produksi: tahu apa yang dilakukan user (analytics) dan apa yang rusak (crash). Selalu bungkus di balik protocol agar vendor dapat diganti.

KebutuhanPilihan umum
AnalyticsFirebase Analytics
Crash reportingFirebase Crashlytics atau Sentry
Error + performance monitoringSentry (gabungan)
Abstraksi vendor-agnostic
// Kontrak — domain tidak tahu Firebase/Sentry
protocol AnalyticsTracking {
    func track(_ event: String, _ params: [String: Any])
}
protocol CrashReporting {
    func record(_ error: Error)
    func setUser(id: String)
}

// Implementasi — satu-satunya tempat import SDK vendor
final class FirebaseAnalytics2: AnalyticsTracking { /* ... */ }
final class SentryCrashReporter: CrashReporting { /* ... */ }
PrinsipTracking call tersebar di seluruh app, jadi jika terikat langsung ke SDK vendor, mengganti vendor berarti menyentuh ratusan tempat. Dengan protocol, ganti vendor = ganti satu implementasi. Ini sekaligus memudahkan mematikan tracking saat test.

07Testing Libraries & Latihan

Quick (BDD spec) & Nimble (matcher ekspresif) populer di era XCTest. Namun di 2026, Swift Testing native (Module 13) adalah default untuk proyek baru — lebih ringkas, terintegrasi, tanpa dependency. Quick/Nimble tetap Anda temui di codebase lama.

ArahanProyek baru: Swift Testing (native, dibahas Module 13). Pertahankan/pahami Quick+Nimble hanya untuk memelihara test suite lama. Nimble masih dipakai sebagian tim karena matcher-nya ekspresif, tetapi pertimbangkan biaya dependency vs ekspresivitas #expect native.

EX 01

Native atau library?

Untuk tiap kasus, native cukup atau perlu library: (a) memuat 1 avatar; (b) list e-commerce 500 gambar dengan prefetch; (c) debounce search; (d) reactive stream kompleks lintas 5 sumber.

▸ Lihat solusi & review

(a) AsyncImage native. (b) Kingfisher (cache + downsampling + prefetch). (c) Combine debounce (atau async + custom debounce). (d) Combine bila benar-benar kompleks; coba async/await dulu.

Review: Library dibenarkan saat native jelas tak memadai (b), bukan kebiasaan. Selalu tanyakan lima pertanyaan di bagian intro.

EX 02

Realm legacy

Klien punya app dengan Realm + Device Sync. Apa nasihat Anda di 2026?

▸ Lihat solusi & review

Device Sync sudah EOL (Sep 2025) — harus migrasi off sync (ke backend sync kustom atau alternatif seperti ObjectBox). Local Realm masih jalan tapi tanpa dukungan resmi. Rekomendasi: dekopel akses Realm di balik Repository (sudah seharusnya), lalu migrasikan persistence ke SwiftData/Core Data secara bertahap.

Review: Karena akses data disembunyikan di Repository (Module 9), migrasi database hanya menyentuh data layer — bukti nyata manfaat abstraksi.

EX 03

Abstraksi vendor

Tim memanggil Analytics.logEvent(...) Firebase langsung di 80 tempat. Klien ingin pindah ke Sentry/Amplitude. Bagaimana seharusnya dari awal?

▸ Lihat solusi & review

Definisikan AnalyticsTracking protocol; semua call lewat abstraksi; Firebase hanya di satu implementasi. Pindah vendor = tulis implementasi baru, ganti registrasi di composition root — nol perubahan di 80 call-site.

Review: SDK vendor adalah detail. Memanggilnya langsung di seluruh app adalah kopling yang mahal dilepas. Bungkus sejak awal.

EX 04

Audit dependency

App mewarisi 14 dependency. Bagaimana Anda memutuskan mana yang dipangkas?

▸ Lihat solusi & review

Untuk tiap dependency, evaluasi lima pertanyaan (intro): apakah ada padanan native sekarang (mis. AsyncImage, async/await menggantikan beberapa), seberapa aktif maintenance, biaya build/binary, dan kesulitan melepas. Pangkas yang sudah ada padanan native & jarang dipakai.

Review: Setiap dependency = utang. Mengurangi dependency menurunkan permukaan serangan (Module 15), waktu build, dan risiko library tak terawat seperti Realm.

08Quiz, Mini-Project, Challenge & Referensi

Quiz Cepat

Jawab dulu di kepala, lalu buka jawaban.

Q1

Kriteria adopsi library

Bagaimana memutuskan memakai library pihak ketiga vs native?

▸ Jawaban

Timbang: masalah yang dipecahkan, kematangan/maintenance, ukuran, dependency transitif, kemudahan penggantian (abstraksi), dan risiko lock-in. Utamakan native bila memadai; adopsi library bila menghemat waktu signifikan pada masalah non-inti dan dapat diabstraksi.

Q2

Realm deprecated

Kenapa Realm tak disarankan untuk proyek baru?

▸ Jawaban

MongoDB men-deprecate Atlas Device Sync (EOL Sep 2025) dan mengurangi investasi. Untuk greenfield, SwiftData/Core Data lebih aman jangka panjang. Verifikasi status terkini sebelum memutuskan.

Q3

Abstraksi library

Kenapa membungkus library pihak ketiga di balik protocol?

▸ Jawaban

Agar dapat ditukar tanpa menyentuh domain, dapat di-mock di test, dan mengisolasi risiko lock-in. Mis. image loader (Kingfisher) di balik protocol ImageLoading.

Mini-Project

Bangun: abstraksi dua libraryIntegrasikan satu image loader (mis. Kingfisher) dan satu crash reporter (mis. Sentry) — keduanya di balik protocol (ImageLoading, CrashReporting). Tunjukkan dapat diganti dengan implementasi lain/mock. Tujuan: disiplin abstraksi & anti lock-in.

Challenge

Naik levelBuat tabel keputusan untuk stack Anda: untuk tiap kategori (DI, reactive, image, analytics, crash, testing) pilih native-vs-library dengan alasan konteks Alhazme. Tantangan: keputusan berbasis trade-off, bukan popularitas.

Common Mistakes

  • Memakai library untuk hal yang native sudah cukup (dependency bloat).
  • Memakai library langsung di domain tanpa abstraksi (lock-in).
  • Mengadopsi Realm untuk greenfield tanpa cek status deprecation.
  • Mengabaikan ukuran & dependency transitif.
  • Tak memantau maintenance/keamanan dependency (M15/M18).

Referensi Resmi

Cari via judul resmi (URL Apple kerap berubah path; verifikasi ke versi terkini):

  • Dokumentasi resmi masing-masing library (repo/website) — verifikasi versi & status terkini.
  • MongoDB — pengumuman status Atlas Device Sync/Realm (verifikasi tanggal EOL terkini).
  • Apple Developer Documentation — alternatif native (SwiftData, Combine, Observation).
