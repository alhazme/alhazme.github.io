01Authentication & Session

Alur: login → simpan token di Keychain → setiap request menyertakan Bearer → refresh otomatis saat 401 → logout membersihkan sesi.

// Domain
protocol AuthRepository {
    func login(email: String, password: String) async throws -> Session
    func logout() async
    var isAuthenticated: Bool { get }
}

struct LoginUseCase {
    let repo: AuthRepository
    func execute(email: String, password: String) async throws -> Session {
        guard email.contains("@") else { throw AuthError.invalidEmail }   // aturan bisnis
        return try await repo.login(email: email, password: password)
    }
}

// Data — token ke Keychain (M5), refresh via interceptor (M10)
final class AuthRepositoryImpl: AuthRepository {
    let network: NetworkService; let tokenStore: TokenStore
    func login(email: String, password: String) async throws -> Session {
        let session: Session = try await network.post("/auth/login",
            body: ["email": email, "password": password])
        try tokenStore.save(session.accessToken, session.refreshToken)   // Keychain
        return session
    }
    func logout() async { tokenStore.clear() }
    var isAuthenticated: Bool { tokenStore.accessToken != nil }
}
Session gating di rootDi entry point, cabangkan berdasarkan isAuthenticated: tampilkan AuthFlow atau MainFlow. Simpan status auth sebagai @Observable yang di-inject via @Environment (M6) agar seluruh app bereaksi terhadap login/logout secara reaktif.

02Role-Based Access Control

Permission adalah aturan domain, bukan pengecekan UI ad-hoc. Modelkan role & permission, gate fitur lewat use case.

enum Permission: String { case viewOrders, editOrders, refund, manageUsers }

struct Role { let name: String; let permissions: Set<Permission> }

@Observable final class SessionContext {          // di-inject via @Environment
    private(set) var role: Role
    init(role: Role) { self.role = role }
    func can(_ p: Permission) -> Bool { role.permissions.contains(p) }
}

// Di View — gate deklaratif
if session.can(.refund) {
    Button("Refund") { vm.refund() }
}

// Di Domain — gate otoritatif (jangan hanya andalkan UI)
struct RefundUseCase {
    let repo: OrderRepository
    func execute(orderID: String, by session: SessionContext) async throws {
        guard session.can(.refund) else { throw AuthError.forbidden }   // enforce di logic
        try await repo.refund(orderID)
    }
}
Prinsip keamananMenyembunyikan tombol di UI bukan kontrol keamanan — hanya UX. Enforcement sebenarnya ada di use case (client) dan di server (otoritatif). Jangan pernah percaya klien: server harus memvalidasi ulang setiap permission. Client-side gate mencegah kesalahan, bukan serangan.

03Offline Mode & Sync

Offline resilience: baca dari cache lokal saat offline, tulis ke antrean saat offline lalu sinkron saat online kembali. Semua di Repository (M9).

final class OrderRepositoryImpl: OrderRepository {
    let remote: OrderRemoteDataSource; let local: OrderLocalDataSource   // SwiftData (M5)
    let syncQueue: SyncQueue

    func fetchAll() async throws -> [Order] {
        do {
            let fresh = try await remote.getOrders()
            try await local.save(fresh)
            return fresh
        } catch is URLError {
            return try await local.loadAll()          // fallback offline
        }
    }

    func place(_ order: Order) async throws {
        try await local.save([order])                 // optimistic write lokal
        do { try await remote.create(order) }
        catch is URLError { await syncQueue.enqueue(.create(order)) }   // antre untuk nanti
    }
}
Konflik & idempotencySaat sinkron antrean berjalan, dua isu muncul: (1) konflik — server & lokal berbeda; tentukan strategi (last-write-wins, server-wins, atau merge). (2) idempotency — operasi antre bisa terkirim dua kali; sertakan client-generated ID/idempotency key (M10). Rancang ini eksplisit; offline yang naif menyebabkan data ganda/hilang.

// Deep link dari notifikasi / Universal Link → Router (M6)
@Observable final class Router {
    var path = NavigationPath()
    func handle(_ url: URL) {
        // https://app.com/orders/123  →  push OrderDetail(123)
        guard url.pathComponents.count >= 3, url.pathComponents[1] == "orders" else { return }
        path.append(OrderRoute.detail(id: url.pathComponents[2]))
    }
}

import StoreKit

func purchase(_ product: Product) async throws {
    let result = try await product.purchase()
    switch result {
    case .success(let verification):
        let transaction = try checkVerified(verification)   // verifikasi tanda tangan
        await transaction.finish()
        // unlock entitlement
    case .userCancelled, .pending: break
    @unknown default: break
    }
}
// Pantau entitlement: Transaction.currentEntitlements & Transaction.updates

EX 01

RBAC enforcement

Seorang engineer hanya menyembunyikan tombol "Refund" dari user tanpa permission. Cukupkah? Apa yang kurang?

▸ Lihat solusi & review

Tidak cukup. UI hiding hanya UX. Enforcement harus di use case (klien) dan — yang otoritatif — di server. User bisa memanggil API langsung.

Review: Aturan keamanan: klien tidak pernah dipercaya. Client-side gate mencegah kesalahan; server-side gate mencegah serangan.

EX 02

Offline write

User membuat order saat offline. Rancang alurnya agar tidak hilang & tidak ganda saat online.

▸ Lihat solusi & review

Tulis optimistic ke lokal + enqueue ke sync queue dengan client-generated ID. Saat online, kirim dengan idempotency key sehingga retry tidak menggandakan. Tangani konflik dengan strategi yang dipilih (mis. server-wins).

Review: Idempotency key + optimistic local write + queue = pola offline resilience standar. Tanpa idempotency, retry queue = data ganda.

EX 03

Payment routing

App Anda menjual (a) langganan premium dan (b) produk fisik UMKM. Mekanisme pembayaran mana untuk masing-masing?

▸ Lihat solusi & review

(a) StoreKit 2 — digital, wajib IAP per kebijakan Apple. (b) Payment gateway (Midtrans/Xendit) — barang fisik di luar IAP.

Review: Salah menaruh barang fisik di IAP melanggar guideline & memotong 15–30% komisi tak perlu; salah menaruh digital di gateway → penolakan App Review. Ketahui batasnya.

EX 04

Deep link testability

Bagaimana Anda menguji bahwa Universal Link /orders/123 membuka layar yang benar tanpa menjalankan seluruh app?

▸ Lihat solusi & review

Karena logika ada di Router.handle(url:) yang murni, unit-test: beri URL, assert path berisi OrderRoute.detail(id: "123"). Tidak perlu UI.

Review: Menyatukan parsing link di satu fungsi murni membuatnya teruji unit — bukti nilai memisahkan navigasi dari View.

08Quiz, Mini-Project, Challenge & Referensi

Quiz Cepat

Jawab dulu di kepala, lalu buka jawaban.

Q1

RBAC

Bagaimana menerapkan role permission dengan aman di klien + server?

▸ Jawaban

Server adalah otoritas: setiap request divalidasi terhadap role/permission di backend. Klien hanya menyesuaikan UI (sembunyikan aksi tak berizin) demi UX — tak pernah sebagai penegakan keamanan. Zero-trust: jangan percaya klaim role dari klien.

Q2

Offline + idempotency

Kenapa operasi offline yang disinkron perlu idempotency key?

▸ Jawaban

Agar retry (setelah koneksi kembali) tak menghasilkan duplikat (mis. order ganda). Klien mengirim idempotency key unik per operasi; server mengabaikan duplikat dengan key sama. Fondasi offline mode andal.

Q3

Deep link

Apa risiko keamanan deep link dan bagaimana menanganinya?

▸ Jawaban

Deep link bisa memicu aksi/otentikasi — validasi & otorisasi tujuannya, jangan percaya parameter mentah. Untuk aksi sensitif, verifikasi sesi & izin sebelum mengeksekusi.

Mini-Project

Bangun: irisan fitur SaaS end-to-endAmbil satu alur (mis. buat order) dan bangun lengkap: auth+RBAC (UI menyesuaikan role), simpan offline dengan idempotency key, sinkron saat online, kirim push saat sukses, dan log terstruktur. Tujuan: menyatukan pilar produksi dalam satu irisan vertikal.

Challenge

Naik levelTambahkan payment (StoreKit 2 untuk konten digital ATAU gateway untuk barang/jasa fisik — pahami perbedaan kebijakan Apple) dan feature flag/kill-switch untuk fitur berisiko. Tantangan: keputusan payment yang benar secara kebijakan + observability sejak awal.

Common Mistakes

  • Menegakkan RBAC hanya di klien (server tak memvalidasi).
  • Sinkron offline tanpa idempotency (duplikat data).
  • Deep link mengeksekusi aksi tanpa validasi/otorisasi.
  • Memakai gateway pihak ketiga untuk konten digital yang seharusnya StoreKit (penolakan App Review).
  • Tanpa observability (log/trace) sejak awal — sulit debug produksi.
