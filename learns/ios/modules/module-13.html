MODULE 13 · PHASE 7 — TESTINGStrategi Testing Production

Arsitektur bersih (Phase 4) membayar dividen di sini: karena logika terpisah dari UI & jaringan, ia dapat diuji cepat & deterministik. Module ini menyusun strategi testing berlapis dengan framework native 2026.

Swift TestingXCUITest~100 menitiOS 27
Testing pyramid: banyak unit test (cepat, murah), sedikit UI test (lambat, mahal, rapuh).
Prinsip alokasiMayoritas kepercayaan berasal dari unit test use case & repository — cepat, deterministik, mudah dipelihara. UI test hanya untuk happy path kritis (login → checkout). Jangan membalik piramida: UI test yang terlalu banyak membuat suite lambat & rapuh (flaky).

01Swift Testing — Framework Native 2026

Swift Testing menggantikan XCTest untuk kode baru: makro @Test, ekspektasi #expect/#require, grouping @Suite, dukungan async/throws bawaan, dan parameterisasi.

Old → New · Framework test
Old — XCTest 
final class MathTests:
  XCTestCase {
  func testAdd() {
    XCTAssertEqual(add(2,3), 5)
  }
}
New — Swift Testing 
import Testing

@Test func add() {
  #expect(add(2, 3) == 5)
}
Migrasi: import Testing; fungsi ditandai @Test (bebas prefix test); XCTAssertEqual(a,b)→#expect(a == b); unwrap wajib #require. XCTest & Swift Testing bisa hidup berdampingan (interop). Alasan: sintaks lebih ringkas & ekspresif (memakai ekspresi Swift biasa), diagnostik lebih baik saat gagal, parameterisasi & async native, tanpa boilerplate class. XCTest tetap dipakai untuk UI test (XCUITest).
Fitur inti
@Suite("Order calculations")
struct OrderTests {
    @Test func totalSumsItems() {
        let order = Order(items: [.init(price: 10), .init(price: 5)])
        #expect(order.total == 15)
    }

    @Test(arguments: [(-1, false), (0, false), (5, true)])   // parameterized
    func isValidQuantity(_ qty: Int, _ expected: Bool) {
        #expect(Order.isValid(quantity: qty) == expected)
    }

    @Test func fetchThrowsOnEmpty() async throws {
        let sut = FetchOrdersUseCase(repository: EmptyRepo())
        await #expect(throws: OrderError.self) { try await sut.execute() }
    }

    @Test func requireUnwrap() throws {
        let user = try #require(makeUser())          // gagal jelas bila nil
        #expect(user.id == "42")
    }
}

02Unit Test — Use Case & Repository

Target utama unit test: use case (aturan bisnis) & repository (mapping/cache). Karena dependency disuntik (M9), Anda memberi mock.

@Test func placeOrderRejectsEmptyCart() async {
    let sut = PlaceOrderUseCase(repository: MockOrderRepository())
    await #expect(throws: OrderError.emptyCart) {
        try await sut.execute(cart: [])                 // aturan bisnis diuji
    }
}

@Test func repositoryMapsDTOToDomain() async throws {
    let mockNetwork = MockNetworkService(stub: [OrderDTO(id: "1", total_amount: 9.99)])
    let repo = OrderRepositoryImpl(network: mockNetwork)
    let orders = try await repo.fetchAll()
    #expect(orders.first?.total == Decimal(9.99))       // mapping benar
}
Kecepatan = frekuensiUnit test yang cepat (tanpa jaringan/DB nyata) dijalankan setiap commit dan menangkap regresi seketika. Ini hanya mungkin bila arsitektur memungkinkan mock — pembayaran langsung dari investasi Clean Architecture Phase 4.

03Mocking Strategy

Mock dibangun dari protocol (M2/M9). Tiga jenis test double:

JenisPeran
StubMengembalikan nilai tetap (kontrol input test)
SpyMerekam pemanggilan (verifikasi interaksi terjadi)
FakeImplementasi ringan berfungsi (mis. in-memory repo)
 
// Spy — merekam apakah save dipanggil
final class SpyOrderRepository: OrderRepository {
    private(set) var savedOrders: [Order] = []
    func place(_ order: Order) async throws { savedOrders.append(order) }
    func fetchAll() async throws -> [Order] { [] }
}

@Test func placingOrderPersists() async throws {
    let spy = SpyOrderRepository()
    let sut = PlaceOrderUseCase(repository: spy)
    try await sut.execute(cart: [Item(price: 10)])
    #expect(spy.savedOrders.count == 1)                 // verifikasi interaksi
}
Hindari over-mockingMock hanya boundary (jaringan, DB, waktu, randomness). Jangan mock tipe domain Anda sendiri — uji mereka langsung. Test yang penuh mock hingga tidak menguji apa pun yang nyata memberi rasa aman palsu.

04UI Test — XCUITest

UI test menjalankan app nyata & mensimulasikan tap/ketik. Lambat & rapuh, jadi batasi pada alur kritis. Tetap memakai XCTest/XCUITest (bukan Swift Testing).

final class CheckoutUITests: XCTestCase {
    func testLoginToCheckout() {
        let app = XCUIApplication()
        app.launchArguments = ["-uitesting"]            // mode test: stub network
        app.launch()
        app.textFields["email"].tap()
        app.textFields["email"].typeText("a@b.com")
        app.buttons["login"].tap()
        XCTAssertTrue(app.staticTexts["dashboard_title"].waitForExistence(timeout: 5))
    }
}
Kunci stabilitasGunakan accessibility identifier (bukan teks yang bisa berubah/terlokalisasi) untuk menemukan elemen. Jalankan UI test terhadap network yang di-stub (via launch argument) agar deterministik — UI test yang memukul server nyata pasti flaky.

05Snapshot Test

Snapshot test merekam render komponen sebagai gambar referensi, lalu membandingkan pada run berikutnya — menangkap regresi visual (layout bergeser, warna berubah). Ideal untuk design system (M6).

// Konsep (mis. library swift-snapshot-testing)
@Test func primaryButtonMatchesReference() {
    let view = PrimaryButton(title: "Bayar")
    assertSnapshot(of: view, as: .image(layout: .fixed(width: 200, height: 44)))
}
DisiplinSnapshot test kuat untuk komponen design system tetapi bisa rapuh terhadap perubahan OS/rendering. Simpan referensi per-konfigurasi (device, mode gelap/terang), tinjau perubahan snapshot seperti code review, dan regenerasi sengaja — bukan otomatis. Snapshot testing biasanya memakai library pihak ketiga; evaluasi biaya dependency (M11).

06Test Architecture & Coverage Gate

Organisasikan test mengikuti struktur modul (M9): tiap package punya test target sendiri. Tegakkan ambang coverage di CI (M14).

  • Struktur — DomainTests, DataTests, FeatureXTests paralel dengan modulnya.
  • Fokus coverage — kejar coverage tinggi di Domain (use case) & Data (repository/mapping), bukan angka global buta.
  • Gate CI — PR gagal bila coverage domain turun di bawah ambang atau test merah (Module 14).
  • Deterministik — tanpa jaringan/waktu nyata; suntik clock & network.
Metrik yang benarCoverage 100% bukan tujuan; coverage tinggi pada logika bernilai (aturan bisnis, edge case, error path) adalah tujuan. Test getter/setter trivial menaikkan angka tanpa menaikkan keyakinan. Ukur "apakah bug tertangkap", bukan sekadar "berapa persen baris tersentuh".

07Latihan

EX 01

Migrasi XCTest → Swift Testing

Konversi: func testDiscount() { XCTAssertEqual(price(100, discount: 0.1), 90) }

▸ Lihat solusi & review 
@Test func discount() {
    #expect(price(100, discount: 0.1) == 90)
}

Review: Tanpa class, tanpa prefix test, memakai ekspresi == biasa. Saat gagal, diagnostik menampilkan nilai aktual kedua sisi.

EX 02

Parameterized test

Uji fungsi isStrongPassword untuk beberapa input sekaligus tanpa menulis banyak fungsi.

▸ Lihat solusi & review 
@Test(arguments: [("abc", false), ("Abcd123!", true), ("12345678", false)])
func passwordStrength(_ input: String, _ expected: Bool) {
    #expect(isStrongPassword(input) == expected)
}

Review: Satu fungsi, banyak kasus. Tiap kasus dilaporkan terpisah — bila satu gagal, Anda tahu input mana.

EX 03

Spy verifikasi

Buktikan bahwa LogoutUseCase memanggil clear() pada token store.

▸ Lihat solusi & review 
final class SpyTokenStore: TokenStore {
    private(set) var cleared = false
    func clear() { cleared = true }
}
@Test func logoutClearsToken() async {
    let spy = SpyTokenStore()
    await LogoutUseCase(store: spy).execute()
    #expect(spy.cleared)
}

Review: Spy memverifikasi interaksi (clear dipanggil), bukan hanya nilai kembalian. Tepat untuk aksi bereffect seperti logout.

EX 04

Alokasi test

App checkout punya budget waktu test terbatas. Bagaimana alokasi antara unit/UI test untuk logika harga, mapping API, dan alur login→bayar?

▸ Lihat solusi & review

Logika harga & mapping API → unit test (banyak, cepat, edge case). Alur login→bayar → satu UI test happy-path kritis. Sisanya cukup unit + integration.

Review: Ikuti piramida. Investasi terbesar di unit (nilai tinggi, biaya rendah); UI test hanya untuk jalur yang kegagalannya fatal.
