01Git Workflow

Untuk solo founder & tim kecil, trunk-based dengan short-lived branch lebih sederhana & cepat daripada git-flow yang berat.

ElemenPraktik
BranchPendek-umur dari main: feat/orders-filter, merge cepat
CommitConventional Commits: feat:, fix:, refactor:, chore:
PRKecil, satu tujuan; CI hijau wajib sebelum merge
Branch protectionWajib PR + status check lulus untuk main
VersiSemantic Versioning: MAJOR.MINOR.PATCH
 
git checkout -b feat/orders-filter
git commit -m "feat: add status filter to orders list"
git push -u origin feat/orders-filter
# buka PR → CI jalan → review → merge ke main
Selaras dengan SDLC AndaIni memetakan langsung ke flow Anda: /new-ticket → /new-spec → code → /pr → merge → /progress-update. Conventional Commits juga memungkinkan changelog & versioning otomatis (mis. semantic-release), mendukung standar Technical Documentation Anda.

02Code Signing

Signing adalah sumber frustrasi terbesar iOS CI. Dua artefak: certificate (identitas developer) & provisioning profile (app + device + entitlement). fastlane match menyimpannya terenkripsi di repo terpisah agar konsisten lintas mesin & CI.

# Setup sekali — simpan cert & profile terenkripsi di git repo privat
fastlane match init
fastlane match appstore        # generate/ambil cert + profile untuk distribusi

# Di CI, match mengambil & meng-install cert yang sama
fastlane match appstore --readonly
Keamanan kredensialPassphrase match, App Store Connect API key, dan token disimpan sebagai encrypted secrets di GitHub (bukan di repo/kode). Gunakan App Store Connect API key (bukan Apple ID + password) untuk autentikasi CI — lebih aman & tak terpengaruh 2FA. Jangan pernah commit .p12/profile/key ke repo utama.

03Fastlane

Fastlane mengotomasi tugas berulang (build, signing, upload, screenshot) lewat lane yang didefinisikan di Fastfile.

# Fastfile
default_platform(:ios)

platform :ios do
  desc "Build & upload ke TestFlight"
  lane :beta do
    match(type: "appstore", readonly: true)          # signing konsisten
    increment_build_number(xcodeproj: "MyApp.xcodeproj")
    build_app(scheme: "Production", export_method: "app-store")
    upload_to_testflight(skip_waiting_for_build_processing: true)
  end

  desc "Jalankan test"
  lane :test do
    run_tests(scheme: "Production")
  end
end
NilaiSatu perintah fastlane beta menggantikan puluhan langkah manual (bump versi, archive, export, upload). Lane yang sama jalan di mesin lokal & CI — reproducible. Ini inti doktrin "automation over manual" Anda: jika berjalan lebih dari dua kali, otomasikan.

04CI/CD Pipeline — GitHub Actions

Workflow menjalankan gate kualitas pada tiap PR, lalu distribusi pada merge/tag.

# .github/workflows/ios.yml
name: iOS CI
on:
  pull_request:
    branches: [main]
  push:
    tags: ['v*']

jobs:
  quality:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - name: Lint
        run: swiftlint --strict
      - name: Test + Coverage
        run: fastlane test
      - name: Coverage gate
        run: ./scripts/check_coverage.sh 70   # contoh ambang — tetapkan sesuai konteks tim/proyek, bukan angka baku

  deploy:
    needs: quality
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - name: Beta
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}
          APP_STORE_CONNECT_API_KEY: ${{ secrets.ASC_API_KEY }}
        run: fastlane beta
Struktur gateJob quality (lint + test + coverage) jalan di setiap PR — mencegah kode buruk masuk main. Job deploy hanya jalan pada tag rilis — memisahkan integrasi dari distribusi. Coverage gate (M13) menegakkan ambang pada logika domain, bukan angka global.

05Build Flavors

Tiga environment (dev/staging/production) dipisahkan lewat scheme + configuration + .xcconfig (M4), sehingga satu codebase menghasilkan build berbeda tanpa perubahan kode.

EnvironmentBundle IDBackend
Devcom.app.devdev API, logging verbose
Stagingcom.app.stagingstaging API, TestFlight internal
Productioncom.appprod API, App Store
PraktikBundle ID berbeda memungkinkan ketiga build ter-install bersamaan di satu device (QA praktis). Nilai per-environment (base URL, key) berasal dari .xcconfig, dikonsumsi CI lewat scheme yang dipilih — bukan hardcode.

06TestFlight & App Store Release Checklist

  • TestFlight — build otomatis via upload_to_testflight; internal testers instan, external butuh review ringan.
  • Metadata — deskripsi, screenshot (bisa via fastlane snapshot), keyword, privacy policy URL.
  • Privacy — App Privacy "nutrition label" (data dikumpulkan) & PrivacyInfo.xcprivacy manifest wajib.
  • Compliance — export compliance (enkripsi), age rating.
  • Review — patuhi App Review Guidelines (mis. IAP untuk digital — M12).
  • Rollout — phased release (bertahap ke % user) agar regresi tertangkap sebelum 100%.
RollbackiOS tidak punya "rollback" instan seperti web — user yang sudah update tetap di versi baru. Mitigasi: phased release + feature flag / remote config untuk mematikan fitur bermasalah tanpa rilis ulang, dan expedited review untuk hotfix kritis. Rancang kemampuan mematikan fitur dari server sejak awal.

07Latihan

EX 01

Rancang gate PR

Apa saja yang harus lulus sebelum PR boleh merge ke main?

▸ Lihat solusi & review

Lint bersih, semua test hijau, coverage domain ≥ ambang, build sukses, minimal satu review approval, branch up-to-date dengan main. Tegakkan via branch protection.

Review: Gate otomatis mencegah "works on my machine". Coverage gate spesifik ke logika bernilai (M13), bukan angka global.

EX 02

Signing di CI

CI gagal build dengan "no matching provisioning profile". Bagaimana pendekatan yang benar?

▸ Lihat solusi & review

Gunakan fastlane match: cert & profile terenkripsi di repo terpisah, di-fetch --readonly di CI dengan MATCH_PASSWORD dari secrets. Autentikasi via App Store Connect API key.

Review: Jangan generate profile ad-hoc di CI; match memberi konsistensi deterministik lintas mesin. Kredensial selalu di encrypted secrets.

EX 03

Hotfix produksi

Fitur baru menyebabkan crash di produksi. Rilis App Review butuh waktu. Apa opsi Anda?

▸ Lihat solusi & review

(1) Matikan fitur via feature flag / remote config (instan, tanpa rilis). (2) Ajukan expedited review untuk hotfix. (3) Untuk rilis bertahap yang belum 100%, hentikan phased rollout.

Review: Karena tidak ada rollback instan di iOS, kemampuan remote-disable harus dirancang sebelum insiden. Ini keputusan arsitektur, bukan reaksi.

EX 04

Lane rilis

Tulis outline lane Fastlane untuk rilis production ke App Store (bukan hanya TestFlight).

▸ Lihat solusi & review 
lane :release do
  match(type: "appstore", readonly: true)
  build_app(scheme: "Production", export_method: "app-store")
  upload_to_app_store(
    submit_for_review: true,
    automatic_release: false,        # kontrol manual saat go-live
    phased_release: true
  )
end

Review: phased_release menyebar rilis bertahap; automatic_release: false memberi kontrol waktu go-live. Metadata & screenshot bisa disertakan di lane yang sama.

09Quiz, Mini-Project, Challenge & Referensi

Quiz Cepat

Jawab dulu di kepala, lalu buka jawaban.

Q1

Trunk-based

Apa keuntungan trunk-based development untuk tim kecil?

▸ Jawaban

Integrasi sering ke main (branch pendek), mengurangi merge hell & drift, cocok dengan CI/CD & feature flag. Untuk solo/tim kecil, mengurangi overhead branching kompleks (mis. GitFlow).

Q2

match (signing)

Masalah apa yang dipecahkan fastlane match?

▸ Jawaban

Menyimpan & menyinkronkan sertifikat/provisioning profile secara terpusat (repo terenkripsi) agar signing konsisten lintas mesin & CI. Menghindari 'signing hell' manual di Xcode.

Q3

Kill-switch

Kenapa kill-switch/feature flag penting untuk rilis?

▸ Jawaban

Memungkinkan mematikan fitur bermasalah tanpa rilis ulang (yang butuh review App Store). Mengurangi risiko rilis; memisahkan deploy dari release (M18).

Mini-Project

Bangun: pipeline CI dasarBuat GitHub Actions workflow: pada PR jalankan lint (SwiftLint) + test; pada tag jalankan build + (mock) upload TestFlight via Fastlane. Signing via match (konsep). Tujuan: automasi quality gate & distribusi.

Challenge

Naik levelTambahkan phased release + rollback protocol dan integrasi kill-switch (feature flag remote) untuk fitur berisiko. Tantangan: pisahkan deploy dari release; siapkan jalur mundur cepat.

Common Mistakes

  • Menyimpan sertifikat/secret di repo tanpa enkripsi.
  • Tanpa quality gate (lint/test) sebelum merge.
  • Signing manual tak konsisten lintas mesin.
  • Rilis tanpa jalur rollback/kill-switch.
  • Menjalankan langkah manual yang berulang (harusnya diautomasi).
