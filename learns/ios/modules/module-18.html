MODULE 18 · PELENGKAP — PRODUCTION READINESSMigration, Privacy & Feature Flags

Tiga hal yang tidak terlihat saat membangun tetapi menggigit keras saat rilis kedua: skema berubah dan app crash, App Review menolak karena privacy, dan fitur bermasalah tak bisa dimatikan. Modul ini menutup ketiganya.

Kenapa krusialRilis pertama mudah. Rilis kedua-lah yang menguji: data user lama harus bermigrasi tanpa crash, binary harus lolos privacy check App Store, dan Anda butuh cara mematikan fitur dari server tanpa menunggu review. Ketiganya harus dirancang sebelum rilis pertama.

01SwiftData Migration

Saat Anda mengubah @Model (menambah field, mengubah relasi), data user lama harus bermigrasi. Perubahan sederhana ditangani lightweight migration otomatis; perubahan kompleks butuh rencana eksplisit.

Kasus produksi — crash saat launch v2Anda rilis v1 dengan Order. v2 menambah field wajib currency: String tanpa default. User lama update → SwiftData tak bisa memetakan store lama → crash saat launch, dan tidak terdeteksi di testing karena Anda menguji dari database kosong. Selalu uji migrasi dari database versi sebelumnya yang berisi data.
Versioned schema — dasar migrasi aman
enum SchemaV1: VersionedSchema {
    static var versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] { [OrderV1.self] }
    @Model final class OrderV1 { var id: String; var total: Decimal
        init(id: String, total: Decimal){ self.id = id; self.total = total } }
}

enum SchemaV2: VersionedSchema {
    static var versionIdentifier = Schema.Version(2, 0, 0)
    static var models: [any PersistentModel.Type] { [Order.self] }
    @Model final class Order { var id: String; var total: Decimal
        var currency: String = "IDR"        // default → lightweight-compatible
        init(id: String, total: Decimal, currency: String = "IDR"){
            self.id = id; self.total = total; self.currency = currency } }
}
Aturan lightweightMigrasi otomatis (lightweight) berlaku bila perubahan aman: menambah field opsional atau ber-default, menambah model, menghapus field. TIDAK otomatis: mengubah tipe, rename tanpa penanda, atau menambah field wajib tanpa default. Untuk itu → custom migration (bagian berikut).

02Custom Migration Plan

enum AppMigrationPlan: SchemaMigrationPlan {
    static var schemas: [any VersionedSchema.Type] { [SchemaV1.self, SchemaV2.self] }
    static var stages: [MigrationStage] {
        [ .custom(
            fromVersion: SchemaV1.self,
            toVersion: SchemaV2.self,
            willMigrate: nil,
            didMigrate: { context in
                // isi currency untuk record lama sesuai logika bisnis
                let orders = try context.fetch(FetchDescriptor<SchemaV2.Order>())
                for o in orders where o.currency.isEmpty { o.currency = "IDR" }
                try context.save()
            }
        ) ]
    }
}

// Pasang saat setup container
.modelContainer(for: Order.self, migrationPlan: AppMigrationPlan.self)
Disiplin migrasi(1) Setiap perubahan skema = versi baru + stage. (2) Uji dari data nyata versi lama, bukan database kosong. (3) Simpan seed database tiap versi untuk regression test migrasi di CI (M14). (4) Karena akses lewat Repository (M9), logika bisnis tak terpengaruh detail migrasi. Core Data punya mekanisme setara (mapping model / progressive migration).

03Privacy Manifest

Apple mewajibkan PrivacyInfo.xcprivacy: mendeklarasikan data yang dikumpulkan, tujuan tracking, dan alasan pemakaian "required-reason API". Binary tanpa deklarasi yang benar ditolak.

Kasus produksi — App Store menolak binaryApp Anda memakai UserDefaults, timestamp file, atau systemUptime (termasuk lewat SDK pihak ketiga seperti Firebase). Ini "required-reason API". Tanpa deklarasi alasan di privacy manifest, upload ditolak dengan email otomatis — sering muncul saat submit, bukan saat build, jadi mengejutkan di menit terakhir.
Bagian manifestIsi
NSPrivacyCollectedDataTypesData dikumpulkan (email, ID, lokasi) + tujuan
NSPrivacyTrackingApakah app melakukan tracking lintas-app
NSPrivacyAccessedAPITypesRequired-reason API + kode alasannya
NSPrivacyTrackingDomainsDomain yang dipakai untuk tracking
SDK pihak ketigaSDK (Firebase, Sentry, dll.) kini menyertakan privacy manifest sendiri + signature. Pastikan versi SDK Anda mendukungnya. App Privacy "nutrition label" di App Store Connect harus konsisten dengan manifest — ketidakcocokan memicu penolakan. Audit tiap dependency (M11) untuk kepatuhan privacy.

04App Tracking Transparency

Jika app melacak user lintas-app (mis. atribusi iklan via Firebase/IDFA), Anda wajib meminta izin ATT sebelum tracking.

import AppTrackingTransparency

func requestTracking() async -> Bool {
    let status = await ATTrackingManager.requestTrackingAuthorization()
    return status == .authorized      // hanya track bila diizinkan
}
// Info.plist WAJIB: NSUserTrackingUsageDescription (penjelasan ke user)
Kasus produksi — atribusi Firebase pecahTanpa prompt ATT (atau bila user menolak), IDFA tak tersedia → data atribusi/kampanye Firebase Analytics tidak lengkap. Banyak tim lupa NSUserTrackingUsageDescription di Info.plist → app crash saat memanggil ATT. Minta izin di momen yang tepat (setelah user paham nilainya), dan tangani penolakan tanpa merusak fungsi inti.

05Feature Flags & Remote Config

Feature flag memisahkan deploy dari release: kode terpasang tapi fitur bisa dinyalakan/dimatikan dari server. Selalu di balik abstraksi (M11).

// Kontrak — domain tak tahu Firebase Remote Config / vendor
protocol FeatureFlagProviding {
    func isEnabled(_ flag: Feature) -> Bool
    func value<T>(_ key: String, default: T) -> T
}
enum Feature: String { case newCheckout, aiRecommendations, promoBanner }

// Pemakaian
if flags.isEnabled(.newCheckout) {
    NewCheckoutView()
} else {
    LegacyCheckoutView()          // fallback aman
}
KegunaanFeature flag memungkinkan: gradual rollout (nyalakan untuk 5% user), A/B test, kill-switch (matikan fitur rusak instan), dan trunk-based development (merge kode belum selesai di belakang flag). Implementasi umum: Firebase Remote Config, atau endpoint config sendiri. Selalu punya default aman bila config gagal di-fetch (fail closed untuk fitur berisiko).

06Kill-Switch & Rollout Strategy

Karena iOS tidak punya rollback instan (M14), kill-switch adalah jaring pengaman utama Anda.

  • Kill-switch per-fitur — tiap fitur berisiko punya flag; matikan dari server saat insiden tanpa rilis ulang.
  • Force-update gate — flag versi minimum; bila server menandai versi app terlalu lama/berbahaya, tampilkan layar "wajib update".
  • Gradual rollout — nyalakan bertahap (1% → 10% → 100%), pantau crash/metrik (M11) di tiap tahap.
  • Maintenance mode — flag global untuk menampilkan layar maintenance saat backend down.
Kasus produksi — fitur baru crash di lapanganFitur checkout baru crash 3% user setelah rilis. Tanpa kill-switch: tunggu expedited review (jam–hari) sementara user terdampak. Dengan kill-switch: matikan newCheckout dari Remote Config → semua user seketika kembali ke checkout lama. Inilah kenapa flag + fallback aman dirancang sebelum insiden, bukan sesudah.

07Latihan

EX 01

Migrasi aman vs butuh custom

Mana yang lightweight, mana yang butuh custom migration: (a) tambah note: String?; (b) ubah price: Int → price: Decimal; (c) tambah status: String wajib tanpa default?

▸ Lihat solusi & review

(a) Lightweight — field opsional. (b) Custom — perubahan tipe butuh transformasi. (c) Custom (atau beri default → jadi lightweight).

Review: Menambah field wajib tanpa default adalah penyebab crash migrasi #1. Beri default bila memungkinkan.

EX 02

Privacy audit

App Anda pakai Firebase Analytics + Crashlytics + menyimpan preferensi di UserDefaults. Apa yang harus ada sebelum submit?

▸ Lihat solusi & review

PrivacyInfo.xcprivacy mendeklarasikan: data dikumpulkan Firebase, required-reason untuk UserDefaults, tracking domains bila relevan. SDK Firebase versi ber-manifest. App Privacy label di App Store Connect konsisten. NSUserTrackingUsageDescription bila memakai ATT.

Review: Ketidakcocokan manifest ↔ nutrition label = penolakan. Audit tiap SDK untuk kepatuhan.

EX 03

Feature flag dengan fallback

Rancang flag aiRecommendations yang aman bila config gagal di-fetch (offline saat launch).

▸ Lihat solusi & review 
func isEnabled(_ f: Feature) -> Bool {
    cachedConfig[f.rawValue] ?? f.safeDefault   // pakai cache lalu default aman
}
// aiRecommendations.safeDefault = false → fitur baru OFF bila ragu

Review: Fitur baru/berisiko default false (fail closed). Cache config terakhir agar tidak bergantung fetch saat launch offline.

EX 04

Insiden produksi

Fitur baru crash 5% user, 2 jam setelah rilis. Urutan tindakan Anda?

▸ Lihat solusi & review

(1) Matikan fitur via kill-switch (Remote Config) — instan. (2) Konfirmasi crash rate turun (Crashlytics/Sentry). (3) Hentikan phased rollout bila masih berjalan. (4) Perbaiki + rilis, ajukan expedited review bila perlu. (5) Post-mortem + tambah test regresi.

Review: Kill-switch dulu (mitigasi cepat), perbaikan kemudian. Ini hanya mungkin bila flag dirancang sebelumnya — keputusan arsitektur, bukan reaksi.

08Quiz, Mini-Project, Challenge & Referensi

Quiz Cepat

Jawab dulu di kepala, lalu buka jawaban.

Q1

SwiftData migration

Bagaimana menangani perubahan skema SwiftData tanpa merusak data user?

▸ Jawaban

Gunakan VersionedSchema untuk tiap versi skema + SchemaMigrationPlan (lightweight untuk perubahan sederhana, custom untuk transformasi kompleks). Uji migrasi dengan seed DB tiap versi di CI agar tak ada kehilangan data saat upgrade.

Q2

Privacy Manifest

Apa fungsi PrivacyInfo.xcprivacy?

▸ Jawaban

Mendeklarasikan jenis data yang dikumpulkan, tujuan, dan penggunaan required-reason API — diwajibkan Apple untuk transparansi privasi & App Review. Beberapa API (mis. akses timestamp file) butuh alasan terdaftar.

Q3

Kill-switch vs feature flag

Apa beda keduanya dan kenapa memisahkan deploy dari release?

▸ Jawaban

Feature flag mengontrol ketersediaan fitur (rollout bertahap, A/B). Kill-switch mematikan fitur bermasalah secara darurat tanpa rilis ulang. Memisahkan deploy (kirim kode) dari release (aktifkan fitur) mengurangi risiko & mempercepat mitigasi.

Mini-Project

Bangun: skema berversi + flagAmbil model SwiftData dan buat VersionedSchema v1→v2 (mis. tambah field) dengan SchemaMigrationPlan. Tambahkan feature flag remote (abstraksi) untuk satu fitur + kill-switch. Tujuan: migrasi aman + kontrol rilis.

Challenge

Naik levelTambahkan Privacy Manifest untuk data yang app kumpulkan + required-reason API yang dipakai, dan rancang rollout bertahap (mis. 10%→50%→100%) dengan jalur rollback. Tantangan: rilis berisiko-rendah dengan mitigasi cepat.

Common Mistakes

  • Mengubah skema tanpa VersionedSchema/migration plan (kehilangan data).
  • Tak menguji migrasi dengan data versi lama sebelum rilis.
  • Mengabaikan Privacy Manifest / required-reason API (penolakan App Review).
  • Fitur berisiko tanpa kill-switch.
  • Rilis 100% langsung tanpa rollout bertahap.
