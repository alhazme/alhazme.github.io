01Siklus Izin & Abstraksi Reusable

Semua izin berbagi mesin-status yang sama. Pahami sekali:

Sekali denied, dialog sistem tak muncul lagi — satu-satunya jalan adalah Settings.

Bungkus tiap izin di balik protocol seragam — agar konsisten, testable (M13), dan tak bocor detail framework ke ViewModel.

enum PermissionStatus { case notDetermined, authorized, limited, provisional, denied, restricted }

protocol PermissionService {
    var status: PermissionStatus { get }
    func request() async -> PermissionStatus
}

// Deep-link ke Settings saat denied — satu helper dipakai semua izin
@MainActor func openAppSettings() async {
    if let url = URL(string: UIApplication.openSettingsURLString) {
        await UIApplication.shared.open(url)
    }
}
Pola penanganan universalDi UI, cabangkan tiap status: notDetermined → tampilkan priming lalu request(); authorized/limited → jalankan fitur (limited: dengan batasan); denied/restricted → tampilkan penjelasan + tombol "Buka Pengaturan" + jalur degradasi. Jangan pernah memanggil request() lagi setelah denied — sia-sia.

02Kamera & Mikrofon (AVFoundation)

Izin kamera/mikrofon paling sederhana — status sinkron + request async.

import AVFoundation

struct CameraPermission: PermissionService {
    var status: PermissionStatus {
        switch AVCaptureDevice.authorizationStatus(for: .video) {
        case .notDetermined: .notDetermined
        case .authorized:    .authorized
        case .denied:        .denied
        case .restricted:    .restricted
        @unknown default:    .denied
        }
    }
    func request() async -> PermissionStatus {
        await AVCaptureDevice.requestAccess(for: .video) ? .authorized : .denied
    }
}
// Mikrofon: ganti .video → .audio (butuh NSMicrophoneUsageDescription)
restricted vs deniedrestricted berarti user tidak bisa mengubahnya (mis. parental control / MDM) — jangan tawarkan "Buka Pengaturan" karena tak akan membantu; cukup jelaskan fitur tak tersedia. denied bisa diperbaiki via Settings. Bedakan keduanya di UI.

03Location (CoreLocation)

Izin paling rumit — delegate-based, punya level (When-In-Use vs Always) dan akurasi (Precise vs Reduced). Bungkus delegate menjadi async.

import CoreLocation

@Observable
final class LocationPermission: NSObject, CLLocationManagerDelegate {
    private let manager = CLLocationManager()
    private var continuation: CheckedContinuation<CLAuthorizationStatus, Never>?

    override init() { super.init(); manager.delegate = self }

    var status: CLAuthorizationStatus { manager.authorizationStatus }
    var isPrecise: Bool { manager.accuracyAuthorization == .fullAccuracy }

    func requestWhenInUse() async -> CLAuthorizationStatus {
        guard manager.authorizationStatus == .notDetermined else { return manager.authorizationStatus }
        return await withCheckedContinuation { cont in
            self.continuation = cont
            manager.requestWhenInUseAuthorization()   // memicu dialog
        }
    }

    // Delegate dipanggil saat status berubah → resume continuation
    func locationManagerDidChangeAuthorization(_ m: CLLocationManager) {
        continuation?.resume(returning: m.authorizationStatus)
        continuation = nil
    }
}
Level & akurasiWhen-In-Use (default, disarankan): lokasi hanya saat app aktif. Always: butuh justifikasi kuat & review lebih ketat — minta hanya bila fitur (geofence, tracking latar) benar-benar butuh, dan setelah When-In-Use diberikan. Precise vs Reduced: sejak iOS 14 user bisa memberi lokasi kasar; cek accuracyAuthorization. Bila butuh presisi sementara (mis. navigasi), minta requestTemporaryFullAccuracyAuthorization(withPurposeKey:) + entri NSLocationTemporaryUsageDescriptionDictionary di Info.plist.
Kasus produksi — minta Always terlalu diniMeminta requestAlwaysAuthorization di launch sering ditolak user & App Review. Pola benar: minta When-In-Use dulu saat fitur dipakai; naikkan ke Always hanya saat fitur latar spesifik diaktifkan, dengan penjelasan jelas. iOS juga akan menanyakan ulang Always secara berkala untuk konfirmasi.

05Notifications (UserNotifications)

import UserNotifications

func requestNotifications() async -> PermissionStatus {
    let center = UNUserNotificationCenter.current()
    do {
        let granted = try await center.requestAuthorization(options: [.alert, .badge, .sound])
        return granted ? .authorized : .denied
    } catch { return .denied }
}

// Cek status saat ini (async)
func notificationStatus() async -> UNAuthorizationStatus {
    await UNUserNotificationCenter.current().notificationSettings().authorizationStatus
}
Provisional — kirim tanpa dialogOpsi .provisional mengirim notifikasi senyap (langsung ke Notification Center, tanpa suara/dialog) tanpa meminta izin dulu — user lalu memutuskan mempertahankan/mematikan dari notifikasi itu sendiri. Bagus untuk menaikkan opt-in. Tambahkan kategori & action (UNNotificationCategory) untuk tombol aksi langsung di notifikasi. Ingat: registrasi remote (APNs) + kirim token ke server dibahas di M12.
Kasus produksi — token push basiToken APNs berubah (reinstall/restore/kadang OS update). Bila server mengirim ke token lama, notifikasi gagal senyap. Wajib: daftarkan ulang & kirim token ke server setiap launch, bukan sekali saja.

06StoreKit 2 — Pembelian

StoreKit 2 (async modern) tidak memakai "izin" tetapi punya flow sendiri: ambil produk → beli → verifikasi → berikan entitlement → dengarkan update & restore.

import StoreKit

// 1. Ambil produk dari App Store Connect
let products = try await Product.products(for: ["com.app.pro.monthly", "com.app.pro.yearly"])

// 2. Beli
func purchase(_ product: Product) async throws -> Bool {
    let result = try await product.purchase()
    switch result {
    case .success(let verification):
        let transaction = try checkVerified(verification)   // verifikasi tanda tangan
        await transaction.finish()                          // WAJIB, agar tak diulang
        return true
    case .userCancelled, .pending: return false
    @unknown default: return false
    }
}

// 3. Verifikasi hasil signed
func checkVerified<T>(_ result: VerificationResult<T>) throws -> T {
    switch result {
    case .verified(let safe): return safe
    case .unverified: throw StoreError.failedVerification
    }
}
Entitlement aktif & listener update + restore
// Cek langganan/pembelian aktif (mis. saat launch & buka fitur premium)
func hasPro() async -> Bool {
    for await entitlement in Transaction.currentEntitlements {
        if case .verified(let t) = entitlement, t.productID.hasPrefix("com.app.pro") { return true }
    }
    return false
}

// Dengarkan transaksi di luar app (renewal, pembelian di device lain) — pasang saat launch
func listenForTransactions() -> Task<Void, Never> {
    Task.detached {
        for await update in Transaction.updates {
            if case .verified(let t) = update { await t.finish() /* grant */ }
        }
    }
}

// Restore — user pindah device / reinstall
func restore() async throws { try await AppStore.sync() }
Wajib untuk kepatuhan & keamanan(1) Tombol Restore Purchases wajib ada (syarat App Review) — panggil AppStore.sync(). (2) Verifikasi tanda tangan tiap transaksi; untuk keamanan penuh, validasi juga server-side (App Store Server API) sebelum memberi entitlement bernilai tinggi — klien tak dipercaya (M15). (3) transaction.finish() wajib, kalau tidak transaksi terus muncul kembali. (4) Ingat batas M12: barang digital wajib StoreKit; barang fisik pakai gateway.

07Best Practices — Ringkasan

PrinsipPenerapan
Info.plist duluTambahkan usage string sebelum memanggil API — hindari crash
Just-in-timeMinta izin saat fitur dipakai, bukan di launch
PrimingUntuk izin sensitif, tampilkan layar penjelasan sebelum dialog sistem
Handle semua statusnotDetermined/authorized/limited/provisional/denied/restricted — jangan asumsikan biner
Degradasi anggunFitur inti tetap jalan bila izin ditolak; tawarkan alternatif
Denied → SettingsJangan re-prompt; arahkan ke Settings + jelaskan manfaat
MinimalkanPilih jalur tanpa/paling sedikit izin (PHPicker, When-In-Use, reduced accuracy)
AbstraksiBungkus di protocol → konsisten, testable, tak bocor ke ViewModel
Observasi perubahanUser bisa cabut izin di Settings kapan saja; cek status ulang saat kembali aktif
Kasus produksi — degradasi anggunApp scan struk butuh kamera; user menolak. Salah: layar kosong/crash. Benar: tampilkan pesan "Kamera diperlukan untuk scan" + tombol Buka Pengaturan + alternatif "Pilih dari Galeri" (PHPicker, tanpa izin) atau input manual. Fitur inti tak pernah buntu total karena satu izin ditolak.

08Latihan

EX 01

Handle denied

User menolak izin kamera. Tulis alur UI yang benar (bukan re-prompt).

▸ Lihat solusi & review

Cek status == .denied → tampilkan penjelasan + tombol "Buka Pengaturan" (openAppSettings()) + alternatif (pilih dari galeri via PHPicker / input manual). Untuk .restricted, jangan tawarkan Settings — cukup jelaskan tak tersedia.

Review: Memanggil request() lagi setelah denied tidak menampilkan dialog — sia-sia. Settings + degradasi adalah satu-satunya jalan benar.

EX 02

Location minimal

Fitur "toko terdekat" butuh lokasi sekali saat dibuka. Level & akurasi apa yang diminta?

▸ Lihat solusi & review

When-In-Use (bukan Always) + akurasi penuh hanya bila perlu presisi; untuk "toko terdekat" reduced accuracy sering cukup. Minta saat fitur dibuka, bukan di launch.

Review: Meminta Always untuk fitur foreground = ditolak user & mengundang skeptis App Review. Selalu minta level minimum yang cukup.

EX 03

Pilih foto tanpa izin

App perlu user memilih 1 foto profil. Pendekatan mana & kenapa?

▸ Lihat solusi & review

PHPicker (.photosPicker) — tanpa izin, tanpa dialog. App hanya menerima foto yang dipilih user. Tidak perlu PHPhotoLibrary sama sekali.

Review: Meminta izin seluruh library untuk sekadar memilih satu foto adalah permintaan berlebihan yang menurunkan trust & bisa dipertanyakan reviewer.

EX 04

StoreKit restore & entitlement

User reinstall app; langganan Pro-nya hilang dari UI. Apa yang kurang di implementasi?

▸ Lihat solusi & review

(1) Cek Transaction.currentEntitlements saat launch untuk memulihkan status. (2) Sediakan tombol Restore Purchases (AppStore.sync()) — wajib App Review. (3) Pasang listener Transaction.updates saat launch. Idealnya validasi server-side.

Review: Entitlement bukan disimpan lokal saja; ia diverifikasi dari StoreKit tiap launch. Tanpa restore + currentEntitlements, user yang sah kehilangan akses berbayar.
