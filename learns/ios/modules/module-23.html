01AuthenticationServices — Sign in with Apple

Sign in with Apple memberi login privat (Apple menyembunyikan email asli via relay). Alur: minta kredensial → terima identityToken (JWT) → verifikasi di server.

import AuthenticationServices

final class AppleSignInCoordinator: NSObject, ASAuthorizationControllerDelegate {
    func start() {
        let provider = ASAuthorizationAppleIDProvider()
        let request = provider.createRequest()
        request.requestedScopes = [.fullName, .email]   // hanya diberikan SEKALI (login pertama)
        let controller = ASAuthorizationController(authorizationRequests: [request])
        controller.delegate = self
        controller.performRequests()
    }

    func authorizationController(controller: ASAuthorizationController,
        didCompleteWithAuthorization authorization: ASAuthorization) {
        guard let cred = authorization.credential as? ASAuthorizationAppleIDCredential,
              let tokenData = cred.identityToken,
              let idToken = String(data: tokenData, encoding: .utf8) else { return }
        // KIRIM idToken ke server → server verifikasi tanda tangan JWT ke kunci publik Apple,
        // cek `aud`/`iss`/`exp`, baru buat sesi. JANGAN percaya klien.
        Task { await AuthService.shared.exchangeAppleToken(idToken) }
    }
}
Aturan App Review & keamanan(1) Jika app menawarkan login sosial pihak ketiga (Google/Facebook), Apple mewajibkan Sign in with Apple juga tersedia — pelanggaran = penolakan rilis. (2) fullName & email hanya dikirim pada login pertama — simpan di server saat itu; login berikutnya tak mengirimnya lagi. (3) Verifikasi identityToken di server terhadap kunci publik Apple; klien hanya kurir. (4) Cek status kredensial saat launch (getCredentialState) untuk mendeteksi user mencabut akses. Kebijakan App Review berubah; verifikasi ke pedoman terkini.

02OAuth via ASWebAuthenticationSession

Untuk OAuth/OIDC (login Google, provider kustom), ASWebAuthenticationSession membuka sesi web aman yang berbagi cookie dengan Safari & menangani callback via URL scheme — cara yang benar (bukan WKWebView mentah, yang tak boleh untuk OAuth).

import AuthenticationServices

func startOAuth(authURL: URL, callbackScheme: String) async throws -> URL {
    try await withCheckedThrowingContinuation { cont in
        let session = ASWebAuthenticationSession(
            url: authURL, callbackURLScheme: callbackScheme) { callbackURL, error in
            if let error { cont.resume(throwing: error) }
            else if let callbackURL { cont.resume(returning: callbackURL) }
        }
        session.prefersEphemeralWebBrowserSession = true   // tak berbagi cookie (privasi)
        session.presentationContextProvider = self
        session.start()
    }
    // callbackURL berisi `code` → tukar ke token di server dengan PKCE
}
PKCE & jangan pakai WebView untuk OAuthGunakan PKCE (code challenge/verifier) untuk public client — mencegah intersepsi kode. Jangan lakukan OAuth di WKWebView: provider memblokirnya (dianggap tak aman, rentan phishing) dan tak berbagi sesi Safari. ASWebAuthenticationSession adalah mekanisme resmi. Pertukaran code→token idealnya di server (client secret tak di device, M15).

03SafariServices — SFSafariViewController

Untuk menampilkan halaman web eksternal (T&C, artikel, kebijakan) tanpa membuat browser sendiri: SFSafariViewController memberi Safari penuh (reader, autofill, keamanan) di dalam app.

import SafariServices

func openTerms(from presenter: UIViewController) {
    guard let url = URL(string: "https://alhaz.me/terms") else { return }
    let safariVC = SFSafariViewController(url: url)
    safariVC.dismissButtonStyle = .close
    presenter.present(safariVC, animated: true)
}
SFSafariViewController vs WKWebViewSFSafariViewController: halaman eksternal apa adanya — dapat keamanan/fitur Safari gratis, tak bisa dikustomisasi/di-inject JS (justru itu amannya). Pakai untuk konten yang Anda tak kontrol. WKWebView: saat Anda perlu kontrol penuh (embed konten milik sendiri, bridge JS). Untuk sekadar "buka link", SFSafariViewController hampir selalu pilihan tepat — lebih aman & hemat kerja.

04WebKit — WKWebView

WKWebView meng-embed konten web dengan kontrol penuh: navigasi, bridge JavaScript↔native, injeksi skrip. Kekuatan besar = tanggung jawab keamanan besar.

import WebKit

final class BridgedWebView: NSObject, WKScriptMessageHandler, WKNavigationDelegate {
    lazy var webView: WKWebView = {
        let config = WKWebViewConfiguration()
        // Bridge: JS memanggil window.webkit.messageHandlers.native.postMessage(...)
        config.userContentController.add(self, name: "native")
        let wv = WKWebView(frame: .zero, configuration: config)
        wv.navigationDelegate = self
        return wv
    }()

    // Terima pesan dari JS
    func userContentController(_ ucc: WKUserContentController,
        didReceive message: WKScriptMessage) {
        guard message.name == "native" else { return }
        // VALIDASI payload — jangan percaya isi dari web
    }

    // Kontrol navigasi — cegah membuka URL berbahaya
    func webView(_ webView: WKWebView, decidePolicyFor navigationAction: WKNavigationAction,
        decisionHandler: @escaping (WKNavigationActionPolicy) -> Void) {
        guard let url = navigationAction.request.url,
              url.scheme == "https" else { decisionHandler(.cancel); return }
        // whitelist domain bila hanya konten sendiri yang diizinkan
        decisionHandler(.allow)
    }
}
Keamanan WKWebView (kritis)(1) Hanya muat konten HTTPS dan idealnya whitelist domain via decidePolicyFor. (2) Bridge JS↔native adalah attack surface — validasi ketat setiap pesan; jangan ekspos fungsi sensitif (akses file, kredensial) ke konten web tak tepercaya. (3) Jangan evaluateJavaScript dengan string yang menyertakan input tak tepercaya (injeksi). (4) Untuk OAuth, gunakan ASWebAuthenticationSession, bukan WKWebView (bagian 02). (5) Isolasi skrip via WKContentWorld bila perlu. Ini penerapan langsung defense-in-depth (M15).

05PDFKit

PDFKit menampilkan, menganotasi, dan membuat PDF. Untuk vertikal Anda: invoice, laporan, kontrak.

Menampilkan PDF
import PDFKit

func makePDFView(url: URL) -> PDFView {
    let view = PDFView()
    view.document = PDFDocument(url: url)
    view.autoScales = true
    return view   // sisipkan via UIViewRepresentable di SwiftUI
}
Membuat PDF invoice (render dari konten)
import UIKit

func renderInvoicePDF(to url: URL, draw: (CGContext, CGRect) -> Void) throws {
    let pageRect = CGRect(x: 0, y: 0, width: 595, height: 842)   // A4 @72dpi
    let renderer = UIGraphicsPDFRenderer(bounds: pageRect)
    try renderer.writePDF(to: url) { ctx in
        ctx.beginPage()
        draw(ctx.cgContext, pageRect)   // gambar teks/tabel/logo invoice
    }
}
Kasus vertikal — invoice e-commerce/UMKMGenerate invoice/nota PDF on-device dari data order (nomor, item, total, pajak) lalu bagikan/simpan. Untuk template kompleks, render lewat layout terstruktur. Tanda tangan/anotasi via PDFAnnotation. Karena dibuat on-device, tak perlu server rendering untuk kasus sederhana — hemat & cepat. Untuk dokumen legal/bernilai tinggi, pertimbangkan penandatanganan resmi di server.

06QuickLook

QuickLook memberi preview file instan (PDF, gambar, Office, dll.) dengan UI sistem — tanpa Anda menulis viewer sendiri.

import QuickLook

final class PreviewSource: NSObject, QLPreviewControllerDataSource {
    let urls: [URL]
    init(urls: [URL]) { self.urls = urls }
    func numberOfPreviewItems(in c: QLPreviewController) -> Int { urls.count }
    func previewController(_ c: QLPreviewController,
        previewItemAt index: Int) -> QLPreviewItem { urls[index] as NSURL }
}

// Presentasikan:
let preview = QLPreviewController()
preview.dataSource = previewSource   // simpan referensi kuat!
presenter.present(preview, animated: true)
Detail penting(1) dataSource di-hold weak oleh controller — simpan referensi kuat sendiri agar tak dealokasi. (2) File harus tersedia lokal (unduh dulu bila remote). (3) QuickLook = preview cepat multi-format; PDFKit = saat butuh kontrol PDF (anotasi, ekstraksi, generate). Untuk "user mau lihat lampiran", QuickLook lebih ringkas.

07Best Practice Lintas-Framework

  • Auth diverifikasi di server — identityToken/OAuth code ditukar & diverifikasi server-side; klien kurir, bukan otoritas.
  • Sign in with Apple wajib bila ada login sosial lain — desain sejak awal (App Review).
  • OAuth via ASWebAuthenticationSession + PKCE — jangan pernah di WKWebView.
  • WKWebView di-sandbox — HTTPS + whitelist domain + validasi bridge; jangan ekspos API sensitif ke web tak tepercaya.
  • SFSafariViewController untuk link eksternal — lebih aman & hemat kerja dari WKWebView untuk konten tak dikontrol.
  • Bungkus di balik protocol — AuthProvider, DocumentPreviewer (M9) → testable, dapat ditukar.
  • Dokumen dari sumber tak tepercaya — perlakukan hati-hati; QuickLook mengisolasi rendering.
EpistemikKebijakan App Review (Sign in with Apple), detail passkey/AutoFill di AuthenticationServices, dan API WebKit berkembang tiap tahun. Verifikasi terhadap dokumentasi Apple & pedoman App Review terkini saat implementasi — contoh di modul ini menunjukkan pola stabil, konfirmasikan detail untuk iOS target Anda.

08Latihan

EX 01

Verifikasi Sign in with Apple

Junior Anda memvalidasi login Apple dengan mem-parse identityToken di klien lalu langsung membuat sesi lokal. Apa masalahnya?

▸ Lihat solusi & review

Klien bisa dipalsukan — token harus diverifikasi di server: cek tanda tangan JWT ke kunci publik Apple, validasi iss/aud/exp/nonce, baru buat sesi. Klien hanya meneruskan token.

Review: Zero-trust: otoritas otentikasi ada di server. Parsing klien untuk UI boleh, tapi bukan dasar kepercayaan.

EX 02

OAuth di WebView

Tim ingin login Google via WKWebView agar "tetap di dalam app". Kenapa ini keliru & apa gantinya?

▸ Lihat solusi & review

Google (dan banyak provider) memblokir OAuth di WebView mentah (rentan phishing, tak berbagi sesi). Gunakan ASWebAuthenticationSession + PKCE — sesi web aman resmi yang tetap terasa in-app.

Review: WebView OAuth adalah anti-pattern keamanan yang diketahui. ASWebAuthenticationSession memenuhi tujuan UX tanpa risiko.

EX 03

Bridge WKWebView

WKWebView Anda mengekspos handler native yang, saat dipanggil JS, mengembalikan token sesi user. Apa risikonya?

▸ Lihat solusi & review

Jika konten web (atau iframe pihak ketiga/ XSS di dalamnya) memanggil handler, token bocor. Jangan ekspos API sensitif ke web; whitelist domain via decidePolicyFor; validasi & minimalkan permukaan bridge; pertimbangkan WKContentWorld terisolasi.

Review: Bridge = attack surface. Prinsip least-privilege: web hanya boleh memanggil operasi tak sensitif yang tervalidasi.

EX 04

PDFKit vs QuickLook

Kapan memilih PDFKit, kapan QuickLook, untuk (a) preview lampiran email user, (b) generate invoice dari order, (c) viewer PDF dengan anotasi?

▸ Lihat solusi & review

(a) QuickLook — preview cepat multi-format tanpa viewer kustom. (b) PDFKit/UIGraphicsPDFRenderer — generate. (c) PDFKit — kontrol anotasi & interaksi.

Review: QuickLook = preview instan; PDFKit = saat butuh membuat/mengontrol/menganotasi PDF.

09Quiz, Mini-Project, Challenge & Referensi

Quiz Cepat

Jawab dulu di kepala, lalu buka jawaban.

Q1

Verifikasi Sign in with Apple

Di mana identityToken diverifikasi dan kenapa?

▸ Jawaban

Di server: verifikasi tanda tangan JWT ke kunci publik Apple + validasi iss/aud/exp/nonce, baru buat sesi. Klien bisa dipalsukan — ia hanya kurir token, bukan otoritas.

Q2

OAuth mekanisme

Kenapa OAuth harus lewat ASWebAuthenticationSession, bukan WKWebView?

▸ Jawaban

Provider memblokir OAuth di WebView (rentan phishing, tak berbagi sesi Safari). ASWebAuthenticationSession + PKCE adalah mekanisme resmi & aman yang tetap terasa in-app.

Q3

WKWebView bridge

Kenapa bridge JS↔native adalah attack surface?

▸ Jawaban

Konten web (atau XSS/iframe di dalamnya) dapat memanggil handler native. Jangan ekspos API sensitif; whitelist domain via decidePolicyFor; validasi & minimalkan bridge; HTTPS only.

Mini-Project

Bangun: login + invoiceImplementasikan Sign in with Apple (kirim token ke server untuk verifikasi — mock server) dan generate invoice PDF (PDFKit/UIGraphicsPDFRenderer) dari data order, dapat di-preview via QuickLook. Tujuan: auth aman + dokumen produksi.

Challenge

Naik levelTambahkan OAuth provider kedua via ASWebAuthenticationSession + PKCE (pastikan Sign in with Apple tetap ada — aturan App Review) dan WKWebView ter-sandbox untuk konten milik sendiri. Tantangan: zero-trust auth + web aman.

Common Mistakes

  • Memverifikasi token Apple/OAuth di klien, bukan server.
  • OAuth di WKWebView (diblokir provider, rawan phishing).
  • Mengekspos API sensitif ke konten web via bridge.
  • WKWebView memuat URL non-HTTPS / tanpa whitelist domain.
  • Menawarkan login sosial tanpa Sign in with Apple (penolakan App Review).
